# Модули

Всё, что приложение умеет сверх окна с двумя панелями, приносят модули: команды
и клавиши за ними, источники дерева, оформление, содержимое панели. Модуль —
обычный пакет, зависящий только от `fc_api`; ни о ядре, ни о соседях он не знает.

Ядро знает модули только по списку в `lib/bootstrap/app_modules.dart`. Убрать
модуль оттуда — значит убрать возможность, а не сломать приложение: без модуля
навигации не походишь по дереву, без файловых операций не скопируешь, но окно
откроется, и справка честно покажет, что команд стало меньше.

## Как выглядит модуль

```dart
class Navigation implements FcModule {
  const Navigation();

  @override
  String get id => 'fc.navigation';        // пространство имён настроек и адрес в журнале

  @override
  String get title => 'Navigation';        // название для справки и списка модулей

  @override
  void install(FcRegistry registry) {
    registry.command((context) => GoUpCommand());
    registry.binding(KeyBinding('Bsp', GoUpCommand.commandId));
  }
}
```

Идентификатор команды объявляется **константой рядом с самой командой**:

```dart
class GoUpCommand extends AppCommand {
  static const String commandId = 'panel.up';

  @override
  String get id => commandId;
}
```

Привязка ссылается на команду по строке не случайно: идентификатор — внешний
контракт, он попадает в настройки (переназначение клавиш хранится по нему), в
справку и в журнал, и должен пережить и переименование класса, и отсутствие
самого модуля. Но внутри модуля, где класс под рукой, писать ту же строку
второй раз незачем: константа делает опечатку ошибкой компиляции.

Обратное верно для тестов: там литерал на месте — он и есть проверка контракта,
а сравнение константы с самой собой ничего не проверяет.

`install` вызывается один раз при сборке — **до** того, как появится приложение.
Здесь только объявления: никакой работы, никаких обращений к службам. Работа,
которую нужно сделать при запуске, — это стартовая команда.

Модуль, которому есть что закрыть при выходе (соединение, файл, изолят),
дополнительно реализует `FcModuleLifecycle`.

## Что можно объявить

| Метод реестра | Что даёт |
|---|---|
| `rootProvider(factory)` | корневой источник дерева; ровно один на приложение |
| `provider(scheme, factory, extensions)` | вложенный источник: архив |
| `addressProvider(scheme, factory)` | источник по адресу: `ssh://user@host/` |
| `command(factory)` | действие приложения; фабрика зовётся на каждый запуск |
| `binding(KeyBinding)` | клавиша за действием; порядок задаёт приоритет |
| `startup(factory)` | команда, которая выполняется один раз при запуске |
| `theme(FcThemeSpec)` | оформление: палитра, размеры, иконки, шрифты |
| `viewport(kind, builder)` | чем рисовать содержимое панели этого вида |
| `service<T>(factory)` | служба для ядра и других модулей |

Провайдер, которому запись по одному обходится дорого (архив пересобирается
целиком, сетевой источник открывает соединение), реализует `BatchedWrites`:
движок операций сообщит ему границы работы, и он применит накопленное разом.

### Модуль поверх внешней программы

Модулю, который стоит над внешним инструментом (`7z`, а позже `unrar`, `ssh`),
нужна служба `ProcessRunner` из API — **не** `dart:io` напрямую. Разница не в
чистоте, а в проверяемости: тесты такого модуля не должны требовать инструмента
на машине, иначе они проходят у одного разработчика и падают у другого. В
`fc_test_kit` лежит `FakeProcessRunner` — он отвечает по сценарию и записывает
все вызовы, так что проверить можно и результат, и то, с какими ключами
программу позвали:

```dart
final runner = FakeProcessRunner(
  reply: (call) => call.command == 'l' ? FakeProcessReply(stdout: listing) : const FakeProcessReply(),
);
final runtime = await testApp(provider: ..., modules: [const SevenZipArchiver()], processes: runner);
...
expect(runner.callsOf('a').single.arguments, contains('-mx=9'));
```

Отсутствие инструмента — обычное состояние, а не поломка: модуль всё равно
устанавливается, схема объявлена, а нехватка всплывает при обращении к файлу
понятной ошибкой. Молчаливое «ничего не происходит» было бы хуже: пользователю
неоткуда узнать, чего не хватает. Подробности — `providers.md`, раздел 10.
| `settings` | раздел настроек этого модуля |

### Положить в буфер обмена

```dart
registry.command((context) => CopyPathCommand(context.resolve<ClipboardService>()));
```

`ClipboardService` объявлен в API, а сделан платформенным модулем. Через
интерфейс, а не прямым вызовом Flutter, по той же причине, что и остальное
платформенное: в тестах он обязан быть подставным. Прогон, трогающий настоящий
буфер машины, незаметно стирает то, что человек за ней только что скопировал, —
поэтому `TestPlatform` подставляет свой буфер по умолчанию, а не по просьбе.

### Спросить пароль

Модулю, которому нужен секрет — пароль к архиву, учётные данные к серверу, —
доступна служба `Credentials`:

```dart
final credential = await credentials.obtain(
  CredentialRequest(realm: '7z:$path', title: 'Encrypted archive', message: name),
);
if (credential?.password == null) throw FsError(path, FsErrorKind.permissionDenied);
```

Окно рисует ядро; модуль не знает ни как спрашивают, ни где помнят ответ.
Ответ запоминается по `realm` — спрашивать на каждое обращение не придётся.
Не подошедший секрет модуль забывает сам (`forget`) и спрашивает заново:
подошёл он или нет, известно только модулю. Подробности и протокол повтора —
`providers.md`, раздел 5.6.

В тестах службу заменяет `FakeCredentials` из `fc_test_kit`: отвечает
заготовленным по очереди и записывает, о чём спрашивали.

### Сказать что-то пользователю

Модулю доступны `app.toasts` — всплывающие сообщения о том, что случилось и уже
закончилось:

```dart
context.app.toasts.show('Show hidden files: On');
```

Ставить окно ради одной строки не нужно, и объявлять службу тоже: она уже есть у
приложения, как `theme` и `background`. Подробности — `widgets.md`, раздел про
всплывающие сообщения.

## Когда что доступно

Порядок сборки — это порядок, в котором что-то появляется:

1. **`install`** — модули объявляют, что предлагают. Служб ещё нет, настроек
   ещё нет, приложения ещё нет.
2. **Граф зависимостей** — по объявлениям строится контейнер. С этого момента
   `registry.services.resolve<T>()` в фабриках работает.
3. **Настройки** — прочитаны с диска. С этого момента работает
   `registry.settings.section(...)`.
4. **Приложение** — собрано. С этого момента у команд есть `context.app`.
5. **Стартовые команды** — выполняются по очереди. Ошибка одной не роняет
   запуск: модуль темы не восстановил оформление — приложение всё равно
   должно открыться.

Отсюда правило: **всё, что нужно прочитать или подключить, читается и
подключается из команд**, а не из `install`. Обращение к службам или настройкам
слишком рано даёт внятную ошибку, а не тихую ерунду.

## Оформление

Значений оформления в `fc_api` нет вовсе — там только роли: `FcColors` называет,
что именно красится, `FcMetrics` — что измеряется, `FcIcons` и `FcFonts` — какие
бывают иконки и шрифты. Числа и цвета приносит тема, и без единой темы
приложение не собирается: красить нечем.

Готовые значения живут в `fc_default_theme`. Своя тема наследуется от них и
переопределяет нужное — переписывать полсотни размеров не приходится:

```dart
class LightColors extends DefaultColors {
  const LightColors();

  @override
  Color get windowBackground => const Color(0xFFF5F5F5);
}

registry.theme(const FcThemeSpec(
  id: 'light',
  title: 'Light',
  brightness: Brightness.light,
  colors: LightColors(),
  metrics: DefaultMetrics(),
  icons: DefaultIcons(),
  fonts: DefaultFonts(),
));
```

Размер всего интерфейса задаётся одним числом: `DefaultMetrics(scale: 0.8)` —
и это уже «крупная» тема.

## Настройки

```dart
class ThemeSettings implements Serializable {
  ThemeSettings({this.themeId = 'default'});

  String themeId;

  @override
  void fromMap(Map<String, dynamic> m) => themeId = extract(themeId, m['themeId']);

  @override
  void toMap(Map<String, dynamic> m) => m['themeId'] = themeId;
}

// в команде модуля:
final settings = scope.section(ThemeSettings.new);
settings.themeId = 'light';
scope.save();                                  // запись отложенная, как и у панелей
```

Раздел лежит в общем файле под именем модуля. Раздел отключённого модуля
записывается обратно как есть — настройки не теряются от того, что модуль
сегодня не включили.

**Из `install` раздел не читается.** Модуль объявляет себя раньше, чем настройки
прочитаны с диска, — а сам файл настроек лежит в домашнем каталоге, который
называет провайдер локальной ФС, создаваемый там же. Поэтому тот, кому раздел
нужен рано, получает не значение, а способ его узнать:

```dart
// LocalFileSystem.install
final settings = registry.settings;
registry.rootProvider((services) => LocalTreeProvider(settings: () => settings.section(LocalFsSettings.new)));
```

Так устроен раздел `fc.local_fs` с единственной пока настройкой
`copyProgressMinBytes` — с какого размера файл копируется с показом хода **внутри
него**. Ход стоит изолята и нативного колбэка на каждый файл: на дереве из
десятков тысяч мелких файлов это дороже самой копии, поэтому ниже порога
(умолчание — мегабайт) остаётся `File.copy`, а объём засчитывается по концу.
Полезное значение зависит от диска: на медленной флешке заметен и мегабайт, на
NVMe не заметны и сто.

## Проверка модуля

Тест собирает **настоящее приложение** с этим модулем — на подставках:
дерево в памяти, окно без системы, настройки в памяти.

```dart
final runtime = await testApp(
  provider: InMemoryTreeProvider([FakeEntry.directory('/home')]),
  modules: [const Navigation()],
);

expect(runtime.commands.commandFor(KeyCombination.parse('Bsp'))?.id, 'panel.up');
```

`testApp` сам добавляет оболочку и подставную платформу и сам всё закрывает
после теста. Проверять стоит и обратное: **приложение собирается без модуля** —
это и есть доказательство того, что он необязателен.

## Чего делать нельзя

- **Зависеть от ядра или от другого модуля.** Всё общее живёт в `fc_api`;
  если чего-то не хватает — его место там, а не в соседнем пакете.
- **Заменять чужую службу.** Контейнер отдаёт по типу одну реализацию;
  два объявления одного типа — это ошибка сборки, а не тихая победа последнего.
- **Работать в `install`.** Он для объявлений; работа — в стартовой команде.
