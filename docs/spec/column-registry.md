# Реестр колонок

**Состояние:** сделано. Отметки по ходу — в §14.

Этап [Б2](../roadmap.md#б2-реестр-колонок). Колонка перестала быть значением
перечисления в ядре и стала **объявлением**: её приносит модуль — так же, как
приносит команду, вид панели, просмотрщик и раздел настроек.

## 1. Чего сейчас нет

Колонок ровно десять, и все они перечислены в `fc_api`:

```dart
enum FsColumn { icon, name, tree, path, ext, size, modified, created, accessed, attributes }
```

Всё остальное про колонку — это `switch` по этому перечислению, и таких мест
четыре:

| Где | Что решает |
|---|---|
| `FsColumnTitle.title` (`column_spec.dart`) | заголовок |
| `_compareByColumn` (`node_sorting.dart`) | сравнение при сортировке |
| `FileTableRow._textFor` (`file_table_row.dart`) | текст ячейки |
| `ColumnLayout.defaults` (`column_spec.dart`) | ширина, выравнивание, видимость |

Причём `switch` в Dart исчерпывающий: **добавить колонку — значит поправить
`fc_api` и все четыре места разом**. Модуль этого сделать не может вовсе, и это
не придирка к стилю, а перекрытая дорога сразу трём этапам роадмапа:

* [Б4](../roadmap.md#б4-права-владелец-и-группа) — права, владелец и группа
  отдельными колонками;
* [Б6](../roadmap.md#б6-тип-по-содержимому) — тип по сигнатуре; **служба уже
  сделана**, а колонки нет именно поэтому;
* [Г5](../roadmap.md#г5-виды-панелей) — «2048×1536» от модуля изображений.

Половина работы, впрочем, уже сделана и записана в
[`panel-node-list.md`](panel-node-list.md), §5: колонка расщеплена надвое общим
идентификатором, ядровая половина отдаёт сравнение (`PanelColumns.comparatorOf`),
экранная — показ. Сегодня этим пользуется один список находок. Здесь механизм
доводится до конца: **половины наполняются объявлениями, а не перечислением**.

## 2. Что получается

Модуль объявляет колонку — и она появляется в меню видимости, в шапке, в
строках и в сортировке. Ни одного `switch` по колонкам не остаётся; `fc_api`
о том, что колонка «размер» вообще бывает, больше не знает.

Заодно чинится то, за что сегодня платит человек: **выключенный модуль перестаёт
стирать раскладку**. `ColumnLayout.fromJson` молча теряет запись, которой нет в
умолчаниях, — а с модулями это значит, что запуск без модуля выбрасывает его
колонку из настроек навсегда. Правило становится тем же, что у разделов
настроек: чужое пишется обратно как есть.

## 3. Колонка — объявление, а не значение перечисления

### 3.1. Три вещи, а не одна

Сегодня `ColumnSpec` — и описание колонки, и выбор человека, и то, что рисуют.
Разделяется на три:

| Вещь | Кто владеет | Где живёт |
|---|---|---|
| **Объявление** — какая колонка бывает и какая она по умолчанию | модуль | реестр, на обеих сторонах |
| **Раскладка** — чем человек её переопределил: порядок, ширина, видимость | человек | `settings.json`, `PanelState` |
| **Показ** — объявления, переставленные и подправленные раскладкой | тот, кто рисует | считается на месте |

Из этого следует главное: **`ColumnLayout` перестаёт быть источником геометрии**
и становится записью человеческого выбора. Умолчаний в нём нет — их знает
объявление; пустая раскладка означает «как объявлено», а не «колонок нет».

### 3.2. Объявление объявляется дважды

Колбэк через границу изолятов не поедет
([`client-server.md`](client-server.md), §3), а колонке нужны обе стороны:
сравнение работает над `FsNode` в ядре, ячейка рисуется из `FileEntry` на
экране. Поэтому объявление регистрируется **по разу на каждой стороне**, одним
и тем же значением:

```dart
class Panels implements FcBackendModule, FcFrontendModule {
  static const _size = ColumnSpec(id: 'size', title: 'Size', width: 64, align: ColumnAlign.end);

  @override
  void installBackend(BackendRegistry registry) {
    registry.column(_size, compare: (a, b) => a.size.compareTo(b.size));
  }

  @override
  void installFrontend(FrontendRegistry registry) {
    registry.column(_size, text: (cell) => formatSize(cell.entry.size));
  }
}
```

Дублирования при этом нет: `ColumnSpec` — одна константа на обе половины, и
разъехаться геометрии негде. Проверяет это тест (§13): собранное приложение
сверяет объявленное на двух сторонах по идентификатору.

Модуль, объявивший колонку только на экране, получит колонку, которую нельзя
сортировать: ядру сравнивать её нечем, и оно возьмёт доводчик по имени. Это не
ошибка сборки — колонка может быть и несортируемой нарочно (значок), — но и не
случайность: `sortable` в объявлении говорит, чего колонка обещает.

### 3.3. `ColumnSpec` — паспорт колонки

Остаётся в `fc_api`: это значение, оно ездит через границу в `PanelState` и
хранится в настройках.

```dart
class ColumnSpec {
  const ColumnSpec({
    required this.id,
    this.title = '',
    this.width = 0,
    this.minWidth = 24,
    this.visible = true,
    this.pinned = false,
    this.flexible = false,
    this.sortable = true,
    this.align = ColumnAlign.start,
    this.inLayout = true,
    this.ownWidth = false,
  });

  /// Имя колонки в настройках и в протоколе: `size`, `fs.owner`.
  final String id;

  /// Заголовок — по-английски, как всё в коде: это ключ перевода.
  final String title;

  final double width;
  final double minWidth;
  final bool visible;

  /// Нельзя скрыть и нельзя увести с места: значок и имя.
  final bool pinned;

  /// Занимает всё оставшееся место. Сегодня такова одна колонка — имя.
  final bool flexible;

  /// По колонке можно сортировать.
  final bool sortable;

  final ColumnAlign align;

  /// Колонка входит в раскладку панели.
  ///
  /// false — колонка есть, но человек её не выбирает и в меню видимости она не
  /// стоит: её ставит себе вид, которому она принадлежит. Такова ветвь дерева.
  final bool inLayout;

  /// Ширину задал человек, а не объявление (см. §4.1).
  final bool ownWidth;
}
```

Три поля переезжают из кода в значение: `title` (был `extension FsColumnTitle`),
`sortable` (был геттер `this != icon`), `flexible` (был геттер `id ==
FsColumn.name`). Все три — свойства **этой** колонки, и знать их должен тот, кто
её объявил.

Два новых. `inLayout` появился под ветвь дерева: в умолчаниях её раньше не было
вовсе, а объявить её нужно — и ячейку, и сравнение она берёт из реестра
наравне со всеми. `ownWidth` — под обещание §4.1: в файл уходит только то, что
человек менял руками.

### 3.4. Ядровая половина: сравнение

```dart
// fc_core_api, BackendRegistry
void column(ColumnSpec spec, {ColumnComparatorFactory? compare});

typedef ColumnComparatorFactory = NodeComparator Function(FcServices services);
```

Фабрика, а не готовый компаратор: сравнению бывают нужны службы — колонке
расширения нужен `FileNaming`, а он собирается из настроек и во время
объявления модуля ещё не существует. То же правило, что у всех фабрик реестра.

Собранное доступно ядру службой `ColumnSorting`:

```dart
abstract interface class ColumnSorting {
  List<ColumnSpec> get declared;
  ColumnSpec? find(String id);

  /// Чем сравнивать; null — сравнения нет, порядок задаст доводчик по имени.
  NodeComparator? comparatorOf(String id);

  /// Правило сортировки, которое эта сборка и правда умеет (§5).
  SortSpec sanitize(SortSpec spec);
}
```

### 3.5. Экранная половина: ячейка

```dart
// fc_ui_api, FrontendRegistry
void column(ColumnSpec spec, {ColumnText? text, ColumnCellBuilder? build});

typedef ColumnText = String? Function(ColumnCell cell);
typedef ColumnCellBuilder = Widget Function(BuildContext context, ColumnCell cell);
```

`ColumnCell` — всё, что ячейке нужно знать, одним значением:

```dart
class ColumnCell {
  final FileEntry entry;

  /// Колонки, показанные рядом: колонка имени смотрит, видна ли колонка
  /// расширения, — и только тогда отделяет расширение от имени.
  final List<ColumnSpec> shown;
  bool shows(String id);

  /// Чем имя делится на имя и расширение (`compound-extensions.md`).
  final FileNaming naming;

  /// Строка под курсором активной панели: значок рисуется иначе.
  final bool selected;

  /// Чем открыть байты строки — значку, если правило спрашивает о содержимом.
  final Content Function(FileEntry entry)? contentOf;
}
```

Значением, а не списком доводов, ради [Б3](../roadmap.md#б3-формат-вывода-колонок):
формат вывода добавится сюда полем, и ни одна подпись не поменяется.

`build` — там, где текста мало: значок типа объекта. Заданы оба — рисует
`build`; не задано ничего — ячейка пуста (так объявляют колонку, которой пока
нечего показать).

Собранное доступно интерфейсу службой `PanelColumns` (`Application.columns`) —
рядом с `PanelViews` и `PanelViewports`, и по той же причине.

## 4. Раскладка: чем человек переопределил объявленное

### 4.1. Настройки хранят выбор, а не геометрию

Формат в `settings.json` не меняется:

```json
"columns": [ { "id": "size", "width": 64, "visible": true }, … ]
```

Меняется прочтение. Раньше список накладывался на `ColumnLayout.defaults`, и
запись без пары в умолчаниях выбрасывалась. Теперь `ColumnLayout` — сам этот
список и есть; накладывается он на **объявленное**, и делает это тот, кто
рисует:

```dart
ColumnLayout shown = app.columns.resolve(panel.columns, extra: panel.source.extraColumns);
```

`resolve` идёт по раскладке, для известного идентификатора берёт объявление и
правит его шириной и видимостью из раскладки; объявления, которых в раскладке
нет, дописывает в конец в порядке объявления.

**Ширина закреплённых колонок из раскладки не берётся вовсе, а ширина прочих —
только если человек её и правда менял** (`ColumnSpec.ownWidth`; в файле это
просто наличие ключа `width`). Причина у обоих правил одна и прежняя
([`models.md`](../models.md)): у значка нет ручки, имя резиновое, числа задаёт
оформление, и однажды сохранённое значение осталось бы навсегда. Раньше это
правило прикрывало только закреплённые; теперь оно общее.

### 4.2. Незнакомая колонка спит, а не пропадает

Идентификатор, которого никто не объявил, `resolve` пропускает — рисовать его
нечем, — но из раскладки **не убирает**. Выключили модуль на один запуск,
включили обратно — колонка на своём месте, своей ширины.

### 4.3. Слияние на возврате

Человек переставил колонки — экран отсылает ядру то, что видит, а видит он
только объявленное. Спящая запись при этом уцелеть обязана, поэтому ядро,
принимая `Arrange(columns:)`, **сливает**: пришедший порядок, затем хранившиеся
идентификаторы, которых в пришедшем нет, — в прежнем порядке между собой.
Это то же правило, по которому переживает запись чужой раздел настроек, и
формулируется оно так же: чужое пишется обратно как есть.

## 5. Сортировка спрашивает колонку

`SortSpec.column` становится строкой. `comparatorFor` перестаёт быть закрытым
перечислением случаев: общие правила остаются («..» первым, `foldersFirst`,
доводчик по имени, направление), а сравнение колонки приходит доводом — от
источника (`PanelExtraColumns.comparatorOf`, §6) или из реестра
(`ColumnSorting.comparatorOf`). `builtInComparatorFor` и `_compareByColumn`
исчезают: их содержимое переезжает в объявления модуля панелей.

Незнакомая или несортируемая колонка в настройках не роняет разбор и не
проверяется в `fc_api` — реестра там нет. Проверяет ядро, когда собирает панель:
колонка, которой оно не знает или которая объявлена `sortable: false`,
заменяется на `name`. Одно место вместо двух проверок в `SortSpec.fromJson` и
`sortBy`.

`sortBy` принимает строку и молча ничего не делает для несортируемой колонки —
как и сейчас.

## 6. Источник просит колонки, а не раскладку

Сегодня источник находок отдаёт **целую раскладку**, собранную из
`ColumnLayout.defaults` с включённой колонкой пути. Так больше нельзя: умолчаний
в ядре не остаётся, а собирать чужую раскладку источнику незачем — ему нужна
одна колонка.

```dart
abstract interface class PanelExtraColumns {
  /// Без чего этот источник не читается: `{'path'}`.
  Set<String> get extraColumns;

  /// Чем сортировать **свою** колонку; null — как объявлено.
  NodeComparator? comparatorOf(String column);
}
```

Просьба едет в `SourceInfo.extraColumns` вместо `SourceInfo.columns`, и
`resolve` включает названные колонки поверх раскладки панели. Наложение живёт
на экране и никуда не сохраняется; ядро, принимая раскладку обратно, видимость
этих колонок из неё **выбрасывает** — своего выбора о них человек не делал.
Заодно через границу перестаёт ездить целая раскладка на каждый показ
источника.

Из-за этого отменяется и запрет править колонки в находках. Раньше `Arrange` с
раскладкой в таком источнике не делал ничего вовсе — иначе просьба источника
записалась бы в настройки человека. Теперь это устроено, а не запрещено: потянув
в находках за границу колонки размера, человек получает то, чего и хотел, а
колонка пути в его настройки не попадает.

Старое имя `PanelColumns` освобождается под реестр (§3.5); интерфейс источника
переименовывается — это одно и то же слово о двух разных вещах, и путать их не
стоит.

## 7. Штатные десять переезжают в модуль панелей

Все десять объявляет `fc.panels`, обеими половинами. Модуль перестаёт быть
чисто экранным и получает `installBackend` — как `LocalFileSystem`, `FileSearch`
и `AttributeEditing`.

| id | Заголовок | Сравнение | Ячейка |
|---|---|---|---|
| `icon` | — | нет, `sortable: false` | `build`: значок типа |
| `name` | `Name` | по имени, естественным порядком | имя целиком или без расширения |
| `tree` | `Tree` | по имени | имя (ветвь рисует вид дерева); `inLayout: false` |
| `path` | `Path` | по каталогу объекта | `entry.directoryPath` |
| `ext` | `Ext` | по расширению (`FileNaming`) | расширение |
| `size` | `Size` | по числу | `formatSize` |
| `modified` | `Modified` | по дате | `formatDate` |
| `created` | `Created` | по дате | `formatDate` |
| `accessed` | `Accessed` | по дате | `formatDate` |
| `attributes` | `Attributes` | по строке режима | `attributes.modeString` |

Русские заголовки остаются в словаре того же модуля — там, где и сейчас.

Выключенный модуль панелей означает «нет ни таблицы, ни колонок» — и это уже
так: `viewport`, `panelView` и сама `FileTable` приходят оттуда же.

## 8. Что перестаёт существовать

* `enum FsColumn` и `extension FsColumnTitle` — целиком;
* `ColumnLayout.defaults`, `ColumnSpec.flexible` как геттер, `FsColumn.sortable`;
* `builtInComparatorFor` и `_compareByColumn` в `node_sorting.dart`;
* `SourceInfo.columns` (заменяется на `extraColumns`);
* `FileTableRow._textFor` и `_showExtension` — весь `switch`;
* запрет править раскладку в чужом источнике (`setColumnLayout` с `return`).

Сравнение значка по типу объекта (`_TypeOrder`) не переезжает: колонка значка
несортируема, щёлкать по ней негде, и код этот сегодня мёртв.

## 9. Имена колонок — внешний контракт

Идентификаторы прежних десяти сохраняются буква в букву, поэтому старый
`settings.json` читается без миграции. Имена — контракт: они лежат в настройках,
в протоколе и в справке.

Из этого же следует, что ссылаться на чужую колонку по имени можно, а зависеть
от объявившего её модуля — нельзя. Тот, кому нужно назвать колонку не свою
(список находок и его `path`), объявляет константу у себя, с причиной в
докблоке. Тот же приём, каким окно сведений зовёт правку атрибутов
(`file_info_commands.dart`).

Колонки модулей живут в своём пространстве имён: `fs.owner`, `content.type`,
`image.size`.

| Что | Где |
|---|---|

| `BackendRegistry.column`, `ColumnSorting`, `PanelExtraColumns` | `fc_core_api` |

| Слияние раскладки при `Arrange` | `lib/core/panel_session.dart` |

## 11. Решения

* **Объявление ездит дважды, а не через границу.** Соблазн — объявить колонку
  один раз и переслать. Нельзя: в объявлении колбэки, а они через порт не
  ходят. Дважды объявленная константа честнее «умного» механизма, который на
  деле пересылал бы только половину.
* **Геометрию несёт объявление, а не раскладка.** Иначе правка оформления не
  дошла бы до тех, у кого уже есть `settings.json`, — ровно та беда, от которой
  сегодня спасает запрет читать ширину закреплённых колонок. Теперь это правило
  общее: в файле лежит только то, что человек менял руками.
* **Незнакомое спит.** Выключение модуля — обычное дело (проверка сборки без
  него — сквозное правило роадмапа), и стирать за это раскладку нельзя.
* **Источник просит колонки, а не раскладку.** Просьба «мне нужен путь» и
  ответ «вот вам девять колонок вот такой ширины» — разные по величине вещи, и
  вторая заставляла ядро знать умолчания, которых у него больше нет.
* **`icon` и `name` остаются закреплёнными.** Без значка и имени строка
  нечитаема, а их ширину задаёт оформление.
* **Идентификаторы прежних колонок не меняются.** Миграция настроек ради
  красивого имени — плохая сделка.

## 12. Чего в первой версии нет

* **Формата вывода** — своего вида даты, размера и прав. Это
  [Б3](../roadmap.md#б3-формат-вывода-колонок), и `ColumnCell` заготовлен под
  него полем.
* **Новых колонок.** Владелец и группа — [Б4](../roadmap.md#б4-права-владелец-и-группа),
  тип по содержимому — [Б6](../roadmap.md#б6-тип-по-содержимому). Здесь только
  механизм: переезд десяти существующих и ни одной новой.
* **Окна раскладки колонок.** Меню видимости остаётся тем же списком флажков в
  настройках вида. Своё окно колонкам просится вместе с редактором правил
  окраски ([А7](../roadmap.md#а7-окраска-строк-по-правилам)) — и делать их
  стоит вместе.
* **Колонок, зависящих от того, чего нет в `FileEntry`.** Строка списка везёт
  ровно то, что нужно её показать, и раздувать её ради колонки нельзя: список
  бывает в десять тысяч строк. Колонке, которой нужно своё знание, понадобится
  свой способ его довезти — вопрос откроется в Б6 и решаться будет там.

## 13. Проверка

**Unit** (`test/model/column_layout_test.dart`).

* `resolvedWith`: пустая раскладка даёт объявленное в порядке объявления;
  порядок и видимость из раскладки перекрывают объявление; ширина — только
  правленая; ширина закреплённой — никогда.

* Перестановка: закреплённые не двигаются и не пропускают других вперёд себя;

## 14. Отметки по ходу

**Сделано целиком:** значения (`ColumnSpec`, `ColumnLayout`, `SortSpec`), оба
реестра, объявления штатных десяти у модуля панелей, слияние раскладки в ядре,
просьба источника набором имён. Проверки §13 закрыты; эталоны не изменились ни
на пиксель, как и обещано.

**Что уточнилось по дороге:**

- *Сравнение стало фабрикой, а не готовым компаратором.* Колонке расширения
  нужен `FileNaming` — словарь составных расширений, собранный из настроек
  (`compound-extensions.md`). Во время объявления модуля служб ещё нет, и
  замкнуть на них константу невозможно. Подпись стала
  `NodeComparator Function(FcServices)` — то же правило, что у всех фабрик
  реестра; реестр зовёт её один раз и запоминает.
- *Ветви дерева понадобилось поле.* Колонка `tree` не входила в умолчания
  вовсе, а объявить её нужно — ячейку и сравнение она берёт из реестра наравне
  со всеми. Объявленная «как все», она встала бы в меню видимости как
  погашенный флажок «Tree», обещающий то, чего таблица не умеет. Отсюда
  `ColumnSpec.inLayout`.
- *Обещание «в файл только правленое» потребовало признака.* Раскладка, которую
  возвращает экран, состоит из объявлений с их ширинами, и писать её как есть
  значило бы заморозить умолчания у каждого, кто хоть раз тронул колонки.
  Отсюда `ColumnSpec.ownWidth`: ширину ставит `resize`, в файле это просто
  наличие ключа `width`. Прежнее правило про закреплённые колонки стало частным
  случаем общего.
- *Подставки тестов оказались настоящим потребителем реестра.* `testPanel`,
  `testCore` и `SessionMirror` собирали панель без объявлений — и получали
  пустую раскладку и сортировку по одному имени. Поймалось это не рассуждением,
  а проверкой: «изменение вида пишется на диск с задержкой» перестала видеть
  запись, потому что `resize('size', …)` не находил колонки. В `fc_test_kit`
  появились `testColumnSorting()` и `testPanelColumns()` — те же объявления,
  что и в настоящем запуске.
- *Запрет править колонки в находках снят.* Раньше `Arrange` с раскладкой в
  таком источнике не делал ничего вовсе — иначе просьба источника записалась бы
  в настройки человека. Теперь ядро выбрасывает из пришедшей раскладки
  видимость тех колонок, которых просит источник, и запрет не нужен: потянув в
  находках за границу колонки размера, человек получает то, чего и хотел.
- *Имя `PanelColumns` переехало.* Одним словом назывались две разные вещи —
  просьба источника и реестр объявлений. Провайдерский интерфейс стал
  `PanelExtraColumns`, освободив имя тому, для чего оно точнее.
