# Иконки файлов: картинкой и от системы

**Состояние:** спецификация к обсуждению. Отметки по ходу — в §15.

Иконка строки перестаёт быть пятью `if`-ами и становится **правилом**: условие
→ источник. Источником бывает глиф шрифта, картинка с диска или тот самый
значок, который человек видит в Finder, — свой у `Safari.app`, документный у
`report.pdf`.

Шаг к настраиваемым панелям. Стоит на службе типов
([`content-types.md`](content-types.md)) и делается после неё.

## 1. Что получается

Сегодня иконку выбирает `FileTypeIcon._iconFor`: каталог, ссылка, исполняемый,
битый — и всё. Обычный файл иконки не имеет вовсе, поэтому `Safari.app`,
`report.pdf` и `archive.zip` в списке неразличимы.

После этой работы:

* правило `{"mask": "*.app", "icon": "system"}` показывает настоящий значок
  приложения;
* правило `{"contentGroup": ["image"], "icon": "image:~/icons/pic.png"}` — свою
  картинку, и по **содержимому**, а не по имени: `photo.dat` тоже картинка;
* флаг «системные иконки» одним переключателем делает список похожим на Finder.

**Из коробки не меняется ничего.** Умолчание — те же глифы FontAwesome, тот же
макет, те же эталоны. Причина не в осторожности: референсный вид — решение
дизайн-системы, а не случайность, и менять его заодно с заведением механизма
значило бы протащить два решения под одним обсуждением.

## 2. Правило: условие → источник

```dart
class FileIconRule {
  final EntryCondition when;
  final IconSource icon;
}
```

Список правил проверяется по порядку, **первое совпавшее выигрывает**. Ровно то
же правило, что у окраски строк, и по той же причине: складывать иконки нельзя,
а порядок — единственное понятное объяснение, почему строка выглядит так.

## 3. Условие — общее с окраской строк

`EntryCondition` живёт в `fc_api` (`src/panel/entry_condition.dart`) и служит
обоим: правилу иконки и правилу цвета из [`file-colors.md`](file-colors.md).

```dart
class EntryCondition {
  final FileMask? mask;             // движок масок уже есть
  final Set<EntryKind>? kinds;
  final bool? hidden;
  final bool? executable;
  final bool? broken;
  final String? scheme;             // 'fs', 'zip', 'sftp'
  final Set<String>? contentType;   // 'png', 'zip'
  final Set<String>? contentGroup;  // 'image', 'archive'

  bool matches(FileEntry entry, {ContentType? content});
}
```

Все заданные условия складываются по «и»; незаданные (`null`) не проверяются
вовсе. Разбор из JSON и обратно — здесь же.

**Почему общее.** Условия у двух правил совпадали бы девятью полями из девяти,
а разошлись бы на десятом — и тогда «покрасить недоступное красным» и «дать
недоступному свою иконку» писались бы по-разному. Два похожих типа с двумя
разборами JSON — это не гибкость, а два места, где чинить одну и ту же ошибку.

**`file-colors.md` правится в том же заходе**: `FileColorRule` становится
`EntryCondition` + цвет. Этап А7 ещё не сделан, и это последний момент, когда
такое слияние бесплатно.

## 4. Источник иконки

Строкой — её разбирает `IconSource` (`fc_api`, чистое значение без Flutter):

| Запись | Что значит |
|---|---|
| `glyph:folder` | роль темы — `FcIcons.folder`, `link`, `asterisk`… |
| `glyph:f07b` | произвольный глиф шрифта иконок темы |
| `image:~/.flex-commander/icons/dart.png` | растровый файл с диска |
| `system` | спросить систему о значке этого объекта |

**Только растр** — `png`, `jpeg`, `webp`, `bmp`: их декодирует сам Flutter, и
новых зависимостей работа не приносит. Вектор (`svg`) потребовал бы
`flutter_svg`, а он нужен по-настоящему только наборам иконок, которых в этой
версии нет (§13).

**Неразобранная запись ничего не рисует и приложение не роняет** — правило
просто пропускается, и проверяется следующее. Файл настроек правят руками, а
опечатка в нём не повод не показать каталог. То же с картинкой, которой нет на
диске или которая не декодировалась.

**`~` разворачивается в домашний каталог.** Писать `/Users/koldoon/...` в файле,
который человек носит между машинами, — значит один раз переехать и потерять
все иконки.

## 5. Откуда берутся системные значки

На macOS их отдаёт `NSWorkspace`. Нативная часть — в раннере, рядом с
перетаскиванием (`macos/Runner/MainFlutterWindow.swift`), канал
`flex_commander/icons`, два метода. Приём проверенный: `NSWorkspace.shared
.icon(forFile:)` там уже вызывается — им рисуется значок под курсором, когда
файлы тащат из окна.

```dart
abstract interface class SystemIcons {
  /// Значок этого объекта: у пакета (`*.app`), тома и файла с назначенной
  /// иконкой он свой.
  Future<Uint8List?> forPath(String path, {required int pixels});

  /// Значок по расширению: у обычного файла он только от него и зависит.
  Future<Uint8List?> forExtension(String extension, {required int pixels});
}
```

**Два ключа, а не один — это главное решение.** У обычного файла значок
зависит только от расширения: тысяча `.txt` в каталоге — это один значок и один
вопрос системе. Свой значок бывает у каталогов (пакеты `*.app`, `*.bundle`),
томов, исполняемых файлов и файлов с назначенной иконкой — их и спрашивают по
пути. Спрашивать всё по пути значило бы на каталоге в тысячу строк сходить в
`NSWorkspace` тысячу раз вместо десяти.

Кто по какому ключу:

| Строка | Ключ |
|---|---|
| каталог, ссылка, исполняемый файл | путь |
| файл без расширения | путь |
| обычный файл с расширением | расширение |

**Размер запрашивается в пикселях**, а не в точках: `NSImage` отрисуется под
экран, и на Retina 13-точечная иконка должна приехать 26 пикселей шириной.
Множитель знает тот, кто рисует, — он его и передаёт.

**Вне локальной файловой системы системного значка нет.** Внутри архива и на
сервере у строки нет имени, которое что-то значит для системы (`realPath`
пуст), — правило с `system` там не совпадает, и проверяется следующее.

**На Windows и Linux реализации нет.** Служба отвечает `null`, и всё падает
обратно на глифы. Место для реализации размечено, обещаний в интерфейсе нет.

## 6. Что рисуется, пока ответа нет

Ответ есть **всегда и сразу** — просто он может быть не окончательным.

Правило, которому нужно то, чего ещё не знают (тип по содержимому, значок
системы), **не совпадает**, и проверка идёт дальше по списку. Дошли до
встроенного хвоста — рисуется сегодняшний глиф. Когда недостающее приезжает,
список правил проверяется **заново, с начала**: новое знание могло совпасть с
правилом, которое стоит выше того, что нарисовано сейчас.

Никаких пустых мест и мигания: строка сперва честно показывает то, что известно
по имени, а потом уточняется. Это и есть причина, по которой служба отдаёт два
ответа сразу:

```dart
({FileIcon now, Future<FileIcon>? later}) resolve(
  FileEntry entry, {
  Content Function()? open,
  bool Function()? stillWanted,
});
```

`later` null — уточнять нечего, строка нарисована окончательно. Это обычный
случай: у каталога и у файла, попавшего под правило по маске, ждать нечего.

## 7. Глиф красится темой, картинка — нет

Глиф — это текст, и он подчиняется теме: `colors.icon`, а под курсором
`colors.iconSelected`. Картинка приходит готовой и **перекраске не подлежит**,
в том числе под курсором. Перекрасить цветной значок приложения в цвет текста
курсора значило бы стереть то единственное, ради чего его показывают, — ровно
тогда, когда на строку смотрят.

Пометка иконку не трогает: она показана фоном и полосой слева. Это правило уже
есть, и здесь оно не меняется.

## 8. Размер и высота строки

Размер иконки — величина темы (`FcMetrics.iconSize`, сегодня 13, равен кеглю).
**Настройкой его можно повысить**: цветной значок в 13 точек мелковат, а весь
смысл системных иконок в том, чтобы их было видно.

| Величина | Как считается |
|---|---|
| размер иконки | `size` из настроек, `0` — как в теме; предел 32 |
| высота строки | `max(rowHeight, size + (rowHeight − iconSize))` — тот же просвет, что у глифа |
| ширина колонки иконки | `iconLeftPadding + size + iconGap − cellPadding` |

Обе величины сегодня считаются в одном месте — `FileTable` (`_rowHeight`) и
`ColumnLayout.defaults` соответственно, — и правило «ширину закреплённой колонки
задаёт приложение, а не файл настроек» этой правкой не нарушается: ширина
по-прежнему вычисляется, просто теперь из размера иконки, а не из константы.

При умолчании (`size: 0`) обе формулы дают ровно сегодняшние 20 и 28 — разметка
списка не двигается, эталоны не пересобираются.

## 9. Службы и где что лежит

| Часть | Место | Почему там |
|---|---|---|
| `EntryCondition`, `FileIconRule`, `IconSource` | `fc_api` | правило видят и панели, и окраска строк, и будущее дерево |
| `FileIcon`, `FileIcons`, `SystemIcons` | `fc_ui_api` | это про показ: `IconData` и `ImageProvider` |
| движок правил, кэш, чтение картинок | `dependency/file_icons` (`fc_file_icons`) | переносимо и проверяется без раннера |
| `SystemIcons` поверх канала + Swift | `lib/modules/icons/`, `macos/Runner` | без своего раннера канала не существует — там же лежит `lib/modules/dnd/` |

`Application` получает `FileIcons? get fileIcons` — необязательная возможность
необязательного типа, третья в ряду после `dragAndDrop` и `contentTypes`.
Модуля нет — панель рисует иконки ровно как сегодня.

Чем рисовать, описано значением:

```dart
sealed class FileIcon {}
class IconGlyph extends FileIcon { final IconData data; }      // красится темой
class IconPicture extends FileIcon { final ImageProvider image; } // не красится
class IconNothing extends FileIcon {}   // место есть, иконки нет — обычный файл
```

## 10. Настройки (раздел `fc.icons`)

```json
{
  "size": 0,
  "system": false,
  "rules": [
    {"kinds": ["directory"], "mask": "*.app", "icon": "system"},
    {"mask": "*.dart", "icon": "image:~/.flex-commander/icons/dart.png"},
    {"contentGroup": ["image"], "icon": "glyph:f03e"}
  ]
}
```

В окно настроек уходят только `size` и `system`: список правил в схему полей не
ложится (флаг, число, строка, выбор), а заводить ради него отдельное окно — это
работа размером с саму задачу. Та же оговорка, что в
[`file-colors.md`](file-colors.md) §4, и то же решение: окно — вместе с
редактором раскладки колонок (Б2), где такой же список.

## 11. Порядок проверки

1. **Правила пользователя** — по порядку, первое совпавшее выигрывает.
2. **Флаг `system`**, если включён: локальной строке — системный значок.
3. **Встроенный хвост** — сегодняшние пять правил: `..` и каталог
   `glyph:folder`, битое `glyph:exclamation`, ссылка `glyph:link`, исполняемое
   `glyph:asterisk`, остальное — пусто.

**Зачем флаг, если есть правила.** Самое частое желание — «покажи как в
Finder» — не должно требовать писать JSON руками. А кому нужно тоньше (глифы у
каталогов, системные значки у приложений), тот пишет два правила: правила стоят
выше флага и перекрывают его.

## 12. Что придётся тронуть в панели

* `FileTypeIcon` перестаёт выбирать сам и спрашивает `app.fileIcons`; выбор
  сегодняшних глифов переезжает во встроенный хвост правил. Виджет становится
  `StatefulWidget`: у него появляется «уточнение приехало» (§6).
* `FileTableRow` получает `contentOf` — им открываются байты для условия по
  содержимому. Не панель целиком: строке нужно ровно одно умение, а не вся
  панель.
* `FileTable` считает высоту строки и ширину колонки иконки от размера (§8).
* `stillWanted` — это `mounted` виджета: строка, уехавшая с экрана, пока запрос
  стоял в очереди, ни байтов не читает, ни системного значка не просит.

## 13. Чего в первой версии нет

* **SVG** и `flutter_svg` — §4.
* **Наборов иконок папкой** (`~/.flex-commander/icons/<набор>/pack.json`):
  запись `image:` заведена так, чтобы набор лёг сверху без ломки.
* **Окна правки правил** — §10.
* **Системных значков на Windows и Linux** — §5.
* **Миниатюр вместо иконок** (превью картинки в строке): это этап Г5, и
  устройство у них другое — читается весь файл, а не заголовок.
* **Своих правил у панели**: правила общие на приложение, как и цвета.

## 14. Проверка

**Unit.**

* `EntryCondition`: складывание по «и», незаданное не проверяется, разбор JSON
  туда и обратно, неизвестный вид строки не роняет.
* `IconSource`: все четыре записи, `~` в пути, неразобранная запись.
* Порядок: первое совпавшее правило выигрывает, а не последнее; правила стоят
  выше флага `system`; встроенный хвост срабатывает последним.
* Правило с `contentType` не совпадает, пока тип неизвестен, и совпадает после.
* Кэш системных значков: обычный файл спрашивается **по расширению** один раз
  на сеанс, `*.app` — по пути; строка без `realPath` не спрашивается вовсе.

**Через `testApp`.**

* Без модуля иконок список выглядит ровно как сегодня — эталон
  `design_anchor_golden_test` не двигается.
* Правило с картинкой применяется; файла картинки нет — рисуется глиф, и
  приложение не падает.
* Правило по содержимому: сперва глиф, после ответа службы — уточнённая иконка,
  и строка перерисовалась ровно один раз.
* `size: 24` поднимает высоту строки и ширину колонки иконки; `size: 0`
  оставляет 20 и 28.

**На живой машине** — проверяет пользователь: значки `*.app`, документов и
томов из `NSWorkspace` в тестах не подделать.
