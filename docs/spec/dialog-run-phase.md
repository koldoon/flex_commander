# Фаза прогона: окно не откатывается к форме

> **Фаза растворилась.** `CommandRunPhase` больше нет: «начиналась ли работа» —
> это `operation != null`, и возвращаться к форме не к чему. Разбор причины
> ниже остаётся верным целиком, включая главное — что `isRunning` отвечал на
> вопрос «крутится ли операция», а спрашивали у него «закончился ли прогон».
> Изменилось только то, чем это выражено: заведённой работой, а не отдельным
> перечислением.

**Состояние:** спецификация от 21.08.2026, работа не начата. Отметки о ходе —
§7; готовый контракт по итогам уедет в [`state.md`](../state.md) и
[`widgets.md`](../widgets.md), а этот файл останется записью о том, что
решалось и почему.

Копирование закончилось, окно закрывается — и на мгновение в нём видна форма
с полями `From` и `To`, та самая, с которой всё начиналось. То же у переноса,
удаления и упаковки. Здесь описано, почему так вышло и чем это лечится.

## 1. Что не так сейчас

Окно параметров и окно хода работы — **одно и то же окно**. Никаких
`showDialog` и маршрутов в приложении нет: `CommandDialogLayer`
(`lib/view/dialogs/command_dialog_layer.dart`) рисует `Stack`-ом всё, что лежит
в `CommandRegistry.openDialogs`, и содержимое каждой рамки берёт у команды —
`command.getDialog(context)`. Рамка живёт по `ValueKey(command.runId)`, то есть
это один и тот же `State` от начала до конца; меняется только то, что внутри.

А внутри — выбор ветки (`transfer_commands.dart`, так же в трёх других
командах):

```dart
final question = this.question;
if (question != null) {
  return CommandDialogQuestion(...);
}
if (isRunning) {
  return CommandDialogProgress(...);
}

return CommandDialogForm(...);   // ← ветка «иначе»
```

Форма стоит последней и потому работает **фолбэком**: как только `isRunning`
становится `false`, окно немедленно откатывается к ней. А `isRunning` гаснет
задолго до того, как окно закроется.

Гасит его `AsyncCommandBase.runOperation`:

```dart
try {
  await operation.result;
} on OperationCanceled {
  // Прервано пользователем.
} finally {
  unawaited(_progress?.cancel());
  unawaited(_requests?.cancel());
  _redraw.cancel();
  _running = false;        // ← окно уже показывает форму
  _question = null;
  _finishRun();
  notifyListeners();       // ← и перерисовывается, чтобы её показать
}
```

Закрывает окно совсем другое место — `AppCommand.submit`:

```dart
try {
  await execute();
  closeDialog();           // ← только здесь
} on FsError catch (failure) {
  error = failure.message;
}
```

Между этими двумя точками — хвост `execute`, и он не пустой
(`TransferCommandBase.execute`):

```dart
try {
  await runOperation(operation, message: moves ? 'Moving…' : 'Copying…');
} finally {
  await resolved.release();
  await source?.release();
  panel.selection.clear();
  await panel.reload();          // ← перечитывание источника
  await _reloadDestination();    // ← и приёмника
}
```

Четыре `await`, из них два — настоящее чтение каталогов. На локальном диске это
десятки миллисекунд, то есть несколько кадров с формой на экране; по SSH это
секунды. Мигание — не хвост анимации (анимаций у окон нет вовсе, `DialogFrame`
рисует статический `ModalBarrier`), а честно отрисованные кадры.

Заметнее оно ещё и оттого, что окно в этот момент **меняет ширину**:
`CommandDialogProgress` задаёт себе долю ширины экрана, а форма облегает
содержимое (`IntrinsicWidth` в `DialogFrame`). Прыжок ширины на старте работы
остаётся и после этой правки — см. §8.

Удаление устроено так же (`RemoveCommandBase.execute` перечитывает панель в
`finally`), упаковка в `zip` и в `7z` — тоже.

### Двойной запуск по `Enter`

В том же промежутке лежит дефект, которого никто ещё не видел, но который
хуже мигания. `Enter` в открытом окне ядро отдаёт команде:

```dart
onSubmit: command.submit,
onDismiss: command.dismiss,
```

Охрана в `AsyncCommandBase.submit` и в `AppCommand.submit` — это `if (isRunning)
return`. В хвосте `isRunning` уже `false`, и охрана **не срабатывает**. Та же
проверка в `TransferCommandBase.execute` (`if (editor == null ||
targets.isEmpty || isRunning) return`) тоже пропускает. Значит, `Enter`,
нажатый в момент завершения — а его в этот момент как раз и нажимают, потому
что на экране форма с кнопкой `Copy`, — запускает копирование второй раз.

Причина у обоих дефектов одна: `isRunning` отвечает на вопрос «крутится ли
операция», а спрашивают у него «закончился ли прогон». Это разные вопросы, и
между ответами на них лежит весь хвост.

## 2. Что получается

Окно после завершения работы — до тех пор, пока не закроется:

```
┌ Copy «archive.dmg» ──────────────────────────────┐
│   Item    Copying…                               │
│   File    archive.dmg                            │
│           4.0 GB of 4.0 GB                       │
│           ▓▓▓▓▓▓▓▓▓▓▓▓▓▓▓▓▓▓▓▓▓▓▓▓▓▓▓▓▓▓▓▓▓▓▓▓   │
│   Total   1 of 1                                 │
│           4.0 GB of 4.0 GB                       │
│           ▓▓▓▓▓▓▓▓▓▓▓▓▓▓▓▓▓▓▓▓▓▓▓▓▓▓▓▓▓▓▓▓▓▓▓▓   │
├──────────────────────────────────────────────────┤
│                        [Background]   [Cancel]   │  ← обе приглушены
└──────────────────────────────────────────────────┘
```

Прогресс **замирает** на последних числах, обе кнопки гаснут, и окно в таком
виде закрывается. Формы не видно ни кадра — ни на локальном диске, ни по SSH,
ни после отмены.

Форма возвращается ровно в одном случае: прогон **не начинался**. Пустой путь
приёмника, каталог не найден, приёмник оказался файлом — всё это ошибки
подготовки, и на них окно по-прежнему остаётся формой с красной строкой внизу:
ввод можно поправить и нажать `Copy` ещё раз.

Ошибка, случившаяся **после** старта работы, форму не воскрешает. Окно
показывает разбор:

```
┌ Copy «archive.dmg» ──────────────────┐
│   Copy failed                        │
│   /backup: permission denied         │
├──────────────────────────────────────┤
│                          [Close]     │
└──────────────────────────────────────┘
```

`Enter` и `Esc` в хвосте не делают ничего: подтверждать нечего, работа кончилась,
окно уходит само. Копирование вторым заходом не запускается.

## 3. Как устроено

### Фаза прогона

`AsyncCommandBase` перестаёт хранить `bool _running` и хранит, где прогон:

```dart
/// Где прогон: не начинался, идёт, кончился.
///
/// Разделение не формальное. «Операция крутится» и «прогон закончен» — разные
/// вопросы, и между ответами на них лежит хвост работы: отпустить аренду,
/// перечитать панели, закрыть окно. Пока это был один флаг, окно в хвосте
/// откатывалось к форме, а `Enter` запускал работу второй раз.
enum CommandRunPhase {
  /// Работа не начиналась: окно показывает форму.
  idle,

  /// Операция идёт: окно показывает ход дела, `Cancel` прерывает.
  running,

  /// Операция кончилась — успехом, ошибкой или отменой, — а команда ещё
  /// доигрывает и окно ещё открыто.
  done,
}
```

* `isRunning => _phase == CommandRunPhase.running` — смысл прежний, и
  `canCancel`, `TaskStatus` и полоса фоновых работ ничего не замечают.
* `bool get isBusy => _phase != CommandRunPhase.idle` — «прогон начался и ещё
  не закрыт окном». Это и есть то, что спрашивали у `isRunning`.
* `runOperation` ставит `running` в начале и `done` в `finally` — там же, где
  сейчас `_running = false`. Охрана на входе — по `isBusy`.
* `submit()` охраняется `isBusy`: `Enter` в хвосте не делает ничего.
* `dismiss()` в фазе `done` без ошибки не делает ничего (окно закроется само),
  с ошибкой — закрывает окно, как сейчас.

Фаза — **инвариант, а не совпадение по времени**: сколько бы `await` ни было в
хвосте у команды, окно из прогресса в форму не вернётся.

### Общий каркас окна

Разбор «вопрос → прогресс → форма» сегодня написан слово в слово четыре раза, и
поправить его в четырёх местах — значит согласиться, что пятая команда повторит
ошибку. Он становится общим — виджетом `AsyncCommandDialog` в `ui_kit`:

```dart
@override
Widget? getDialog(BuildContext context) => AsyncCommandDialog(command: this, form: _form);
```

В `ui_kit`, а не методом самой `AsyncCommandBase`, потому что зависимость идёт
`ui_kit → api`: базе, живущей в `api`, взять `CommandDialogProgress` неоткуда.
Разделение при этом получается правильное — в `api` фаза прогона, в `ui_kit`
то, как она выглядит.

Порядок веток внутри:

1. `question != null` → `CommandDialogQuestion`;
2. `isBusy && error == null` → `CommandDialogProgress`, где
   `onCancel: isRunning ? cancel : null` и
   `onBackground: isRunning ? sendToBackground : null`;
3. `isBusy && error != null` → `CommandDialogConfirm` с `failureMessage`,
   текстом ошибки и единственной кнопкой `Close` — ровно то, что сегодня руками
   написано у удаления;
4. иначе → `form(context)`.

`String get failureMessage => '$label failed'` переопределяется: у обеих команд
удаления это `Delete failed`, потому что `label` у одной из них — `Delete !`.

Подписку на команду (`ListenableBuilder`) ставит само окно: оно же и решает, что
показывать.

### Кнопки, которые можно погасить

`CommandDialogProgress.onCancel` становится `VoidCallback?`. `FcButton` уже
принимает `null`: рисует подпись с `opacity: 0.5`, не берёт курсор и не
нажимается.

У «Background» одного этого мало: сейчас кнопки нет вовсе, когда
`onBackground == null`, и в хвосте она бы не погасла, а исчезла — ряд
переставился бы ровно в момент завершения. Поэтому у окна появляется
`canBackground`: он про то, **бывает** ли у этой работы фон, а `onBackground` —
про то, можно ли спрятать её **сейчас**.

## 4. Почему так, а не иначе

* **Не закрывать окно сразу по концу операции.** Соблазнительно: работа
  сделана, а перечитывание панелей — дело приложения, у панелей есть свой
  признак занятости (ошибку чтения они и показывают сами, в своей строке
  состояния, — `PanelController._load` её ловит и наружу не пускает). Но
  окно нужно живым не только хвосту: `operation.result` бросает не одну
  `OperationCanceled`, и всё, что не отмена, доходит до `AppCommand.submit`
  уже **после** того, как `runOperation` вернул управление. Закрыв окно
  раньше, пришлось бы разделять исходы («на успехе закрыть, на ошибке — нет»),
  то есть завести ту же фазу, только неявную.
* **Не переносить хвост внутрь `runOperation`.** Если между `_running = false` и
  `closeDialog()` не останется ни одного `await`, кадра с формой действительно
  не будет: `notifyListeners` только помечает виджеты грязными, а кадр рисуется
  на следующем такте. Но это держится на **отсутствии** `await` — любой
  следующий вернёт мигание, и виноват в нём будет тот, кто добавил безобидную
  строку. Фаза таких обязательств ни на кого не накладывает.
* **Не гасить последнее состояние.** Числа последнего отчёта — честный итог, а
  не мусор, и замерший на них прогресс читается как «готово». Троттлинг тут не
  мешает: `_onProgress` пишет `_state` **всегда** и ограничивает только
  перерисовку, поэтому финальный `notifyListeners()` в `finally` рисует
  настоящий конец, а не то, что троттлинг успел пропустить.
* **Почему `Cancel` гаснет, а не остаётся.** В фазе `done` прерывать нечего:
  `cancel()` при `!isRunning` закрывает окно — то есть кнопка с подписью
  «Cancel» делала бы не то, что на ней написано, и притом на работе, которая
  уже сделана. Живая кнопка, которая ничего не отменяет, хуже серой.
* **Почему `done`, а не `finishing`.** Фаза одна и на успешный хвост, и на
  разбор ошибки, где ничего уже не «финиширует». `done` описывает прогон, а не
  занятие команды.
* **Каркас в базе, а не общий виджет.** Виджету пришлось бы отдавать полтора
  десятка полей `AsyncCommand` наружу и обратно; база и так их все имеет. В
  `ui_kit` остаются куски вида, в `api` — правило, какой кусок когда.

## 8. Что остаётся за рамками

* **Скачок ширины на старте работы.** Форма облегает содержимое, а прогресс
  берёт себе долю ширины экрана, поэтому окно меняет размер, когда работа
  начинается. После этой правки прыжок остаётся ровно один и на своём месте —
  там, где содержимое окна действительно меняется. Чинится он в другом слое
  (ширина окна на весь прогон задаётся рамкой, а не содержимым) и своей работой.
* **`OpenPathCommand`.** У него свой `_running` и своя пара `submit`/`dismiss`,
  но окна хода работы нет — мигать нечему. Приводить его к общей фазе имеет
  смысл только вместе с прогрессом, если он там появится.
* **Что делает `Esc` в хвосте.** Сейчас — ничего. Можно было бы считать его
  просьбой убрать окно немедленно, не дожидаясь перечитывания панелей, но это
  отдельное решение: убранное окно означает, что об ошибке хвоста пользователь
  не узнает.
