# Просмотрщик markdown

**Состояние:** сделано. Отметки по ходу — в §15.

Этап [Г19](../roadmap.md#г19-просмотрщик-markdown). `F3` на `.md` показывает
свёрстанный документ, а не разметку строками; `F5` возвращает исходник.

## 1. Зачем

`README.md`, заметки, спецификации этого самого проекта — всё это сегодня
открывается решётками и звёздочками. Файл, который **написан, чтобы его
читали**, единственный показывается в том виде, в каком его правят.

Но главное в этапе не вёрстка. Библиотека для неё уже стоит в проекте
(`flutter_markdown_plus` в `fc_updater` рисует ею описание выпуска), и сама по
себе вёрстка — работа на день. Главное — **точка расширения**: врезка
` ```mermaid ` должна рисоваться диаграммой, а рисовать её должен **другой
модуль**, ничего не зная о просмотрщике, и просмотрщик — ничего о диаграммах.

Поэтому этап делается в таком порядке: сперва контракт расширения, потом показ,
и только потом — первый его потребитель (этап
[Г20](../roadmap.md#г20-диаграммы-mermaid)).

## 2. Точка расширения: `MarkdownBlockSpec`

### 2.1. Почему в `fc_ui_api`, а не в общем пакете-обёртке

Первым замыслом было объявлять рисовальщика **службой**
(`registry.service<T>` + `services.resolveAll<T>()`), а контракт держать в
kit-пакете: так не пришлось бы трогать общий API.

**Это не работает.** `serviceBindings` — `Map<Type, …>`
(`lib/bootstrap/registrations.dart:67,143`): второй модуль, объявивший ту же
службу, молча затирает первого. `resolveAll<T>` возвращает список, но до него
доезжает ровно одна привязка на тип — и все нынешние потребители в проекте
кончаются `.firstOrNull`, потому что это приём «служба есть или нет», а не «их
много». Двух рисовальщиков блоков так не объявить вовсе.

Объявление, которое должен найти **другой** модуль, проходит через реестр, а
реестр — это `FrontendRegistry`, и живёт он в `fc_ui_api`. Значит и тип
объявления обязан жить там же. Делается он по тому же образцу, что `viewer`,
`packer` и `column`: значение-объявление в API → метод на реестре → ядро только
складывает и упорядочивает → спрашивает тот, кто показывает.

### 2.2. Контракт

```dart
class MarkdownBlockSpec {
  const MarkdownBlockSpec({
    required this.id,        // 'mermaid' — устойчивое имя
    required this.title,     // 'Mermaid diagrams' — для человека
    required this.accepts,   // bool Function(String language)
    required this.build,     // Widget Function(BuildContext, MarkdownBlockRequest)
    this.priority = 0,       // больше — раньше спрашивают
  });
}

class MarkdownBlockRequest {
  final String language;   // первое слово info-строки, в нижнем регистре
  final String source;     // текст врезки как написан
  final String metadata;   // хвост info-строки
  final double maxWidth;   // сколько места дают
}

class MarkdownBlockRefused implements Exception { final String reason; }
class MarkdownBlockDeclined implements Exception {}
```

**`accepts` решает по имени языка, а не по содержимому** — тот же раздел
обязанностей, что у `ViewerSpec.accepts` и `ViewerRefused`: «моё ли это по
имени» против «моё, но вот беда». Иначе `accepts` разбирал бы текст дважды:
один раз чтобы согласиться, второй — чтобы нарисовать.

**`maxWidth` доводом, а не `LayoutBuilder` у потребителя**: диаграмме нужна
ширина **до** раскладки, иначе её не во что вписывать. Ставит `LayoutBuilder`
показ — один раз и одинаково для всех.

**`BuildContext`, а не тема доводом**: `FcTheme.of(context)` доступно любому,
кто зависит от `fc_ui_kit`, а зависеть от него модулю можно. Довод-тема означал
бы, что `fc_ui_api` знает про `FcTheme` из kit, — а он про него не знает и знать
не должен.

**Работа синхронная.** Блоков в документе немного, а показ, начинающийся с
пустого места, хуже показа, начинающегося сразу. Долгое виджет делает внутри
себя сам.

### 2.3. Два рода отказа — как у просмотрщиков

* `MarkdownBlockDeclined` — «это не мой язык», спрашивают следующего;
* `MarkdownBlockRefused(причина словами)` — взялся и не смог: показ рисует
  **исходный текст врезки и причину над ней**.

Чужое исключение ловится тоже: ошибка в чужом модуле не должна уносить весь
документ — врезка показывается с общей фразой, остальной документ цел.

Никого не нашлось — обычная врезка кода с подсветкой. Ни пустого места, ни
молчания: по правилам приложения нажатие и показ обязаны что-то давать.

## 3. Что объявляет модуль показа

```dart
registry.viewer(ViewerSpec(
  id: 'markdown',
  title: 'Markdown',
  priority: 50,                    // выше текста (−100), ниже картинок (100)
  accepts: (entry, type) => …,     // md, markdown, mdown, mkd
  open: (request) => …,
));
```

`TextViewer.extensions` не трогаем: он перечисляет `md` и `markdown` и остаётся
**запасным**. Выключите `fc_markdown_viewer` — и `.md` снова откроется текстом;
это и есть проверка того, что возможность приносит модуль.

## 4. Как перехватывается врезка

Разбор (`markdown 7.3.1`) из ` ```mermaid ` делает `<pre><code
class="language-mermaid">`, а хвост info-строки кладёт атрибутом
`data-metadata` на `pre`.

**Ловушка:** для тега `pre` библиотека **безусловно** заворачивает результат в
`Container(decoration: styleSheet.codeblockDecoration)`
(`flutter_markdown_plus-1.0.12/lib/src/builder.dart:476-481`) — даже если блок
отрисовал наш builder; у соседнего `hr` проверка `builders.containsKey` есть, у
`pre` нет.

Обходить её своим `md.BlockSyntax` — плохой обмен: он отнял бы `data-metadata` и
заставил заново написать разбор ограждений (тильды, отступы, незакрытые блоки).
Поэтому рамка **обезоруживается**: `codeblockDecoration` в общем стиле пустая, а
рисует рамку наш же builder — одинаково для обычных врезок и никак для
диаграммы.

Побочная польза, ради которой это стоит делать и само по себе: подсветки во
врезках кода сейчас нет **нигде** (`SyntaxHighlighter.format(String)` языка не
получает). Наш builder язык знает и зовёт `re_highlight` напрямую.

## 5. Документ строится поблочно

`Markdown` отдаёт готовый список в `ListView(children: …)`, **не** в
`ListView.builder` (`widget.dart:414,581`): виджеты строятся все разом. На
`docs/roadmap.md` этого проекта — 3700 строк, 350 КБ — так строятся тысячи
виджетов до первого кадра.

`MarkdownBuilder` при этом **экспортирован** пакетом, и `build(List<md.Node>)`
даёт по виджету на узел верхнего уровня. Значит документ режется по узлам, а
список строится своим `ListView.builder`.

Предел размера — как у текста: настройкой и `ViewerRefused` со словами.

## 6. Документ, а не сплошной текст

`.md` — документ, и выглядеть он должен документом:

* **колонка в три четверти ширины**, полями по краям. Строка во всю ширину
  читается плохо: глаз теряет начало следующей. Поля даёт отступ списка, а не
  рамка вокруг него, — полоса прокрутки остаётся у края области, где её и ищут
  рукой;
* **поля сверху и снизу** — один раз на документ, а не у каждого блока;
* **отбивка над заголовком**, и тем больше, чем заголовок крупнее. Сверху, а не
  снизу: заголовок принадлежит тому, что под ним, и без отбивки сливается с
  концом предыдущего раздела. Разный размер отбивки отличает часть от
  подраздела, не читая.

Числами, а не ролями темы: это раскладка одного экрана, а новая роль потянула бы
за собой оформление по умолчанию, редактор тем и макет. Исключение — отбивка
заголовка: она считается от `dialogSectionGap`, потому что смысл у него ровно
этот.

Линейки таблицы рисуются цветом `columnDivider` — тем же, каким панель делит
колонки: таблица в документе и таблица файлов рисуют одно и то же, и разными им
быть незачем. Оформление общее, поэтому так же выглядят и таблицы в окне
обновления.

Текст в ячейках стоит **слева направо и сверху вниз** — так таблицу и читают.
По центру заголовок отрывался бы от своей колонки, а выравнивание по середине
высоты разводило бы строку с одной строчкой и строку с тремя. Явное
выравнивание колонки (`|:---:|`) при этом слушается: его написал автор
документа.

**Ширина колонок — по содержимому, а не поровну.** Поровну плохо тем, что
колонка «Да/Нет» получает столько же места, сколько колонка с описанием на три
строки: одна стоит полупустой, другая переносится впятеро чаще, чем нужно.

Считается общепринятая пара ширин из автоматической раскладки таблиц CSS
(CSS 2.1, §17.5.2.2): **наименьшая** — ширина самого длинного слова, уже неё
колонку сжимать нельзя, слово порвётся; и **наибольшая** — ширина содержимого
без единого переноса. Дальше распределяет сам `RenderTable`: начинает с
наибольших, а не влезло — снимает лишнее, упирая каждую колонку в её
наименьшую. Короткая упирается сразу и дальше не сжимается, длинная забирает
недостачу на себя. Это и есть «равномерно справедливое» распределение, к
которому приходят и консольные таблицы, и вёрстка страниц. Остаток, если места
**больше** чем нужно, делится по наибольшим ширинам — по содержимому, а не
поровну.

Своя `TableColumnWidth`, а не готовая `IntrinsicColumnWidth`, которая считает то
же самое: показ смотрит на **тип** ширины и, увидев готовую, заворачивает
таблицу в горизонтальную прокрутку (`builder.dart:448`) — то есть даёт ей
бесконечную ширину, и длинный текст не переносится вовсе. Своя той проверке не
отвечает, и таблица остаётся в отведённой ширине.

Поля в ячейках — те же, что у затенённой врезки, и углы скруглены тем же
радиусом: таблица и врезка оба «вставленный кусок», и разными им быть незачем.

**Маркеры списков прижаты к правому краю своей колонки** — и точка, и номер, и
флажок. Показ прижимает вправо только номер, а точку центрует: у точки выходит
втрое больший зазор до текста, и на глаз она висит сама по себе. Зазор от
маркера до текста — `checkboxGap`, тот же, что у флажка до его метки: маркер
списка и есть знак при подписи, а библиотечный вдвое меньше, и текст стоял к
точке вплотную.

**Флажок списка задач — наш**, тот же, что в окнах, а не значок Material:
значок рисуется чёрным и в тёмной теме выглядит дырой. Трогать его нельзя —
документ показывают, а не правят, — но и приглушать незачем: приглушённое в
приложении означает «недоступно», а здесь это просто отметка в тексте. Ради
этого квадратик со знаком выделен из `FcCheckbox` в отдельный `FcCheckboxMark`:
подпись в списке задач рисует разметка, и флажку она не нужна. Стоит он у того
же края, что точка и номер, и отбит от текста тем же зазором — то есть выглядит
ровно как флажок в окне.
Черта `---` отбивается сверху наравне с мелким заголовком: вплотную к
предыдущему абзацу она читается его подчёркиванием, а не границей частей.

Ширина **колонки**, а не области, уходит и в `MarkdownBlockRequest.maxWidth`:
иначе диаграмма вылезала бы за поля.

## 7. Показ и исходник

`F5` — «Format / Raw», та же клавиша и тот же смысл, что у форматтеров
([Г3](../roadmap.md#г3-форматтеры-и-json)) и у вектора
(`image-viewer.md`, §14.3).

Raw — не голый текст, а сегодняшний показ: то же поле и та же подсветка
(`code_language.dart`: `md` → `markdown`). Переключатель обязан давать то, что
было до этапа, а не хуже.

**Документ листают с клавиатуры.** Стрелки идут строками, `PageUp`/`PageDown` и
пробел — почти экраном (с нахлёстом в десятую часть, чтобы не терять место
чтения), `Home` и `End` — к краям. К краям **в обоих видах и одними и теми же
клавишами**: в исходнике библиотека вешает голые `Home` и `End` на край строки,
а документ отдаёт по `Ctrl`-версии — в показе это читается как «клавиша не
работает», потому что каретки не видно, а вбок текст обычно и не едет. Поэтому
просмотрщику они переназначены на край документа; редактору край строки
остаётся — там каретку видно.

`End` в свёрстанном виде прыгает **не один раз**: предел прокрутки у ленивого
списка — оценка по средней высоте построенного, и пока построены одни короткие
абзацы, конец документа кажется гораздо ближе, чем он есть. Завышенную оценку
Flutter поправляет сам, заниженную — нет: прыжок упирается в никуда. Значит,
прыгаем, пока предел двигается, но не больше десяти раз. Показ просит клавиши себе: во весь экран
сразу, в области панели — только когда в него вошли, потому что до этого
стрелки принадлежат списку файлов.

## 8. Место чтения переезжает вместе с видом

`F5` не должен отбрасывать человека в начало документа. Длины у свёрстанного
вида и исходника разные, и общего у них только одно: **какой блок сейчас
сверху**. По нему место и переносится — в одну сторону блок превращается в
строку исходника, в другую строка находит свой блок.

Строку спрашивают у того вида, который уходит, и ставят тому, который приходит.
Ставят **сверху**, а не «показывают»: подвести строку к ближнему краю значило бы
при прыжке вперёд оставить её внизу экрана, и место чтения уехало бы на целый
экран.

И ставят **сразу**: человек не просил никуда ехать, он переключил вид. Показ,
который после переключения куда-то едет сам, читается как чужое действие.

В исходнике это прыжок в пикселях: перенос по словам выключен, высота строки
одна на все, и место считается умножением. Высоту строки, однако, знает только
**нарисованное** поле, поэтому прыжок случается кадром позже первой отрисовки —
и этот кадр поле держат невидимым. Показать его значило бы показать текст не на
том месте; на глаз это и есть «очень быстрая прокрутка». Невидимым, но живым:
не нарисовавшись, поле высоту строки не сообщит, а прыгать вслепую — тот же
кадр не на том месте. Высота не пришла за пять кадров — показываем как есть:
пустое поле хуже поля не на той строке. В свёрстанном виде так нельзя —
высоту блока знает только построенный блок, а ленивый список строит лишь
видимое. Поэтому показ не **подводят** к блоку, а **начинают** с него: блок,
с которого читают, становится точкой отсчёта прокрутки, всё, что выше, уходит
в её отрицательную часть и строится, только если туда поднимутся.

Так было не сразу. Сначала список подводили прикидкой «доля от всей длины» с
доводкой в несколько кадров. На ровном документе она попадает точно — и потому
выглядела рабочей, — а на неровном промахивается, список прыгает несколько
кадров подряд и доезжает уже плавностью. Это и увидел человек: показ едет сам.
Точка отсчёта убирает и прыжки, и плавность: место оказывается на месте первым
же кадром.

Курсор для этого не годится: в показе стрелки крутят текст, а не водят курсор, —
он остаётся там, где был. Видимую строку называет само поле, через указатель
слева; номеров строк в markdown не показываем, и указатель в этом случае пустой.

**Позиций узлов библиотека не хранит.** `Element` знает тег, детей и атрибуты — и
ничего о том, из какой строки он взялся; в `BlockParser` номер есть, но наружу
не выходит. Поэтому карта «блок → строка» строится **поиском по тексту**:
у блока берётся начало его первой строки, у строк исходника — то же начало, и
сравниваются они по одним буквам и цифрам, без разметки. Так `## Заголовок` в
исходнике узнаётся в узле «Заголовок», а `**жирный** текст` — в «жирный текст».

Ищут курсором вперёд: найденное не может оказаться выше предыдущего блока. Это
и спасает от повторяющихся заголовков — их в документе бывает много, и только
порядок отличает один «Проверка» от другого. Врезке кода достаётся строка
ограды, а не первая строка кода; разделителю — черта, у него текста нет вовсе.
Не нашли за пятьсот строк — оставляем курсор: место чтения сместится, но не
улетит.

Точность проверена на четырёх настоящих документах проекта — `roadmap.md`,
`release-notes.md`, `README.md` и этой спеке: 1589 блоков, ни одного промаха.

## 9. Поиск: два контроллера

`FcTextFinder` построен на `CodeLineEditingController` из `re_editor` — это
текстовый буфер. В свёрстанном документе текста нет, есть дерево виджетов.

Поэтому экран держит **два** контроллера:

* исходник — им показывают Raw;
* **проекцию видимого текста** — по ней ищут в свёрстанном виде.

`FcSearchable.finder` отдаёт тот, что соответствует режиму. Найденное
превращается в место на экране картой «строка проекции → блок документа»: экран
подписан на поиск, по совпадению узнаёт блок и просит показ его показать.

Ищут **по видимому тексту, а не по разметке**: человек ищет то, что читает, и
звёздочки находиться не должны.

**Ограничение первой версии:** подсвечивается блок целиком, а не слово. Слово
внутри свёрстанного абзаца потребовало бы перехватывать построение всех
текстовых тегов.

## 10. Клавишам нужен свой раздел

`KeyBinding.conflictsWith` (`app_command.dart:235`) считает спором совпадение
клавиши **и контекста**. Г3 повесит `F5` в `KeyContext.textViewer`; положи
markdown туда же — окно настройки клавиш показало бы несуществующий спор двух
`F5`, которые никогда не действуют одновременно. Заводится
`KeyContext.markdownViewer`.

## 11. Картинки и ссылки — через источник

Относительные пути разрешаются **тем же источником**, откуда пришёл документ, а
не через `dart:io`: `.md` открывают и в архиве, и по `ssh`. Разрешитель приходит
в экран замыканием — так он остаётся проверяемым подставным.

Ссылки: внешняя уходит системе; относительная и якорь — **пока** не переход, а
сообщение с разрешённым путём. Переход требует решить, что происходит с панелью
и историей, и это отдельный разговор (§13).

**Удалённые картинки не забираются.** Показ файла не должен молча ходить в сеть:
человек нажал `F3` на документе, а не согласился на запросы к чужим серверам.
Вместо картинки стоит подпись и хост — видно, что здесь было и куда смотреть.
Значки в `README` поэтому не видны; это осознанный размен, а не недосмотр.

Векторная картинка рисуется вектором: значки в репозиториях почти всегда `svg`,
и показывать их рамкой было бы обиднее всего.

## 12. Набор синтаксиса

Набор **свой**, собранный из готовых правил, а не `ExtensionSet` из коробки.

Замысел был взять `gitHubWeb` — он богаче умолчания библиотеки. Выяснилось, что
одно его правило показ роняет: `AlertBlockSyntax` делает из `> [!NOTE]` узел
`div`, а `div` не числится среди блочных тегов отрисовки
(`builder.dart:13-32`), и разбор падает с «Bad state: Too many elements» прямо
в построении виджетов. Настройкой это не чинится: библиотека умеет ровно свои
теги.

Поэтому набор собран поимённо — всё из `gitHubWeb`, **кроме** `AlertBlockSyntax`:
фенсы, якоря заголовков, таблицы, списки задач, сноски, зачёркивание, эмодзи,
автоссылки. Сноски при этом есть уже в `gitHubFlavored`, и тег `section`
отрисовка знает — они работают.

Один и тот же набор идёт и в наш разбор, и в показ: разойдись они — разъехались
бы и узлы.

## 13. Чего в первой версии нет

* **Перехода по внутренним ссылкам** — см. §11.
* **Правки** — просмотрщик ничего не пишет; правят по `F4`.
* **Подсветки слова в свёрстанном тексте** — см. §9.
* **Оглавления документа** — это отдельное окно, а не показ.
* **Загрузки удалённых картинок** — см. §11. Если понадобится, это настройка с
  умолчанием «не ходить», а не поведение по умолчанию.
* **Врезок GitHub** (`> [!NOTE]`, `> [!WARNING]`) — они показываются обычной
  цитатой. Чтобы рисовать их врезкой со значком, нужен свой builder на тег
  `div`: объявленный блочным, он добавит `div` в список блочных тегов отрисовки
  и снимет то самое падение (§12). Работа небольшая, но это отдельный разговор,
  а не хвост этого этапа.

## 14. Проверка

* реестр пуст — показ ведёт себя как без расширений вовсе;
* повторное имя в реестре — ошибка сборки, как у просмотрщиков и упаковщиков;
* `F3` на `.md` открывает markdown, `notes.txt` — по-прежнему текстовый;
* `F5` возвращает исходник с подсветкой и обратно, **не теряя места чтения**:
  блок сверху переходит в строку исходника и обратно в тот же блок; карта
  «блок → строка» сверяется и на настоящих документах проекта, а не только на
  образце;
* поиск в свёрстанном находит видимый текст и **не** находит разметку;
* `Declined` → спрашивают следующего; `Refused` → врезка с причиной на экране;
  чужое исключение → документ цел;
* `docs/roadmap.md` (350 КБ) открывается и прокручивается;
* **выключен модуль** — `.md` снова открывает текстовый;
* живьём — проверяет пользователь.

## 15. Отметки по ходу

**Шаг 1 — контракт и ядро.** Сделан 28 сентября 2026 года.
`MarkdownBlockSpec`, `MarkdownBlockRequest` и два отказа объявлены в
`fc_ui_api`; `FrontendRegistry.markdownBlock`, `Application.markdownBlocks`,
складывание с проверкой повтора по имени и упорядочивание по убыванию
приоритета — на месте. Шесть проверок в `test/app/markdown_blocks_test.dart`.

*Замысел со службой не пережил проверки исходников.* Он казался дешевле — не
трогать общий API, — и был неверен: `serviceBindings` это `Map` по типу, второй
объявивший молча затирает первого (§2.1). Хорошо, что проверили до кода, а не
после того, как два рисовальщика начали бы исчезать через одного.

*Тест на повторное имя сперва ловил не то.* Два модуля в нём назывались
одинаково, а `installAll` пропускает модуль с уже занятым идентификатором
(`registrations.dart:90`) — второй просто не устанавливался, и проверка
доказывала работу чужой защиты вместо своей. Модули разведены по именам.

**Шаг 2 — пакет `fc_markdown_kit`.** Сделан 28 сентября 2026 года. Оформление
переехало из окна обновления, появились врезка кода с подсветкой, разбор
документа на блоки и ленивый показ. 22 проверки в пакете; окно обновления
показывает то же, что и раньше, — его виджет-тесты (49) зелёные.

*Ленивость проверена, а не объявлена.* Документ из трёхсот блоков строит только
видимые: тест ищет текст последнего блока и не находит его, пока до него не
долистали. Это и был главный риск шага — звать `MarkdownBuilder.build` по
одному узлу никто так не делает, — и он не подтвердился: `build` чистит своё
состояние в начале и честно отдаёт виджеты переданных узлов.

*Выбор набора синтаксиса оказался неверен, и это нашли тесты.* В спеке стоял
`gitHubWeb`; на врезке `> [!NOTE]` показ падает — подробности в §12. Набор
пересобран поимённо, спека исправлена, а сама врезка честно записана в §13 как
то, чего в первой версии нет.

*Подсветка врезок — побочная польза, ради которой рамку и пришлось отнимать у
библиотеки.* Её не было **нигде**: подсветке отдают только текст, без языка.
Теперь код в окне обновления подсвечен, и это первое видимое за два шага.

**Шаг 3 — модуль `fc_markdown_viewer`.** Сделан 29 сентября 2026 года. `F3` на
`.md` показывает свёрстанный документ, `F5` возвращает исходник и запоминает
выбор, предел размера — полмегабайта. 19 проверок в пакете, включая сборку без
модуля.

*Предел свой, а не текстовый.* У текста он сто килобайт и стоит из-за подсветки,
читающей файл целиком; здесь документ строится лениво, и полмегабайта покрывает
даже `docs/roadmap.md` этого проекта — треть мегабайта. На этом есть отдельная
проверка: возьми мы текстовый предел, самый большой документ в репозитории
перестал бы открываться.

*Слово «Format» оказалось занято.* Оно уже значит формат файла — «Формат» у
архивов и картинок, — и доктринальная проверка переводов честно не дала
объявить второй смысл. Развели оговоркой `context: 'markdown'`, как и принято в
проекте.

*Эталоны не пострадали, и это проверено, а не понадеялось.* Новый раздел
настроек должен был сдвинуть снимок окна настроек; локально все снимки и так
красные по причине, к работе отношения не имеющей (иная отрисовка шрифтов на
macOS 27), и отличить «уже красное» от «сломал я» на глаз нельзя. Померили
иначе: расхождение в процентах с модулем и без него совпало до пикселя на всех
трёх затронутых снимках — значит раздел в кадр не попадает.

**Разбор на стороне, стоивший времени.** Содержимое тестовых файлов писалось
через `String.codeUnits` — это UTF-16, а не байты UTF-8, и кириллица в
документе поехала. Поймал это тест, сравнивавший исходник; будь сравнение
только по числу блоков, ошибка уехала бы дальше.

**Шаг 4 — поиск и картинки.** Сделан 29 сентября 2026 года. Проекция видимого
текста, поиск в обоих видах, подсветка найденного блока и картинки по
относительным путям. 13 новых проверок в модуле и 6 в пакете показа.

*Проекция оказалась главным в шаге, а не поиск.* Сам поиск — это готовые
команды из `fc_text_kit`; работа была в том, чтобы превратить дерево виджетов в
строки и запомнить, какая строка какому блоку принадлежит. Ячейки таблицы идут
через табуляцию, врезка кода — своими строками, разделитель строки не занимает:
иначе номера поехали бы, и найденное подсвечивалось бы не там.

*Удалённые картинки решено не забирать.* Спека этого не предписывала, и решение
принято здесь: показ файла не должен молча ходить в сеть. Записано в §11 и §13
вместе с ценой — значки в `README` не видны.

**Прокрутки клавишами не было вовсе** — нашлось на живой проверке, после
выпуска. Свёрстанный показ не просил себе фокус, и ни стрелки, ни страницы до
него не доходили: документ листался только мышью. Это прямое нарушение правила
«нажатие обязано что-то менять», и обидное — в показе текста прокрутка есть с
самого начала, а здесь её просто забыли. Добавлена вместе с четырьмя
проверками, включая ту, что выше начала листать некуда.

*Первая правка кода по итогу теста.* Проверка «за сеть никто не просил» поймала,
что чтение запускалось в `didChangeDependencies` **до** того, как показ смотрел
на схему адреса: разрешителя звали и для `https://…`. Теперь чтение начинается
только для соседнего файла.

**Разбор на стороне, стоивший времени.** Проверка «картинка показана» не
находила виджета, хотя он стоял в дереве: картинка в тесте 1×1, абзац с ней
почти нулевой высоты, и `find` считал её невидимой. Лечится флагом
`skipOffstage: false`. Полчаса ушло на поиск расхождения между пробой и тестом,
которого в коде не было вовсе.

**Шаг 5 — документ выглядит документом.** Сделан 29 сентября 2026 года по
замечанию с живой проверки: показ читался сплошным текстом от края до края, а
заголовки сливались с предыдущим разделом. Появились колонка в три четверти
ширины, поля сверху и снизу и отбивка над заголовками по их размеру (§6).
Семь проверок, в том числе на то, что **без этих доводов показ ведёт себя
по-прежнему**: окно обновления рисует markdown тем же пакетом, и менять его вид
этот шаг не должен был.

Заодно по тому же замечанию линейки таблиц переехали на `columnDivider`. Это
общее оформление, так что изменились и таблицы в окне обновления — намеренно:
две таблицы в одном приложении не должны быть разными.

*Ячейки оказались центрированы не там, где казалось.* Тело таблицы библиотека и
так кладёт влево; по центру стояли **заголовок** (`tableHeadAlign` из запасного
набора) и вертикаль (`tableVerticalAlignment`, у неё умолчание `middle`).
Поправлены оба, и проверка стоит не на полях набора, а на живом дереве: у
ячейки с тремя строчками и у соседки с одной верхние кромки должны совпадать.

**Место чтения переезжает вместе с видом.** По замечанию с живой проверки:
`F5` отбрасывал в начало документа. Перенос сделан по блоку, который стоит
сверху (§8); карта «блок → строка исходника» строится поиском по тексту, потому
что позиций узлов библиотека не хранит вовсе.

*Точность проверена на настоящих документах, а не только на примере.* Порядок
блоков, ограда врезки, повторяющийся заголовок — это всё видно и на коротком
образце; а вот попадёт ли ключ в строку на документе в треть мегабайта,
показывает только сам документ. На `roadmap.md`, `release-notes.md`, `README.md`
и этой спеке: 1589 блоков, ни одного промаха. Две находки оттуда и пришли:
номер нумерованного списка в узел не попадает (`1. раз` даёт «раз»), и снимать
его со строки исходника надо **до** обрезки ключа, иначе ключ строки выходит
короче искомого; а у разделителя текста нет вовсе, и искать его надо по виду.

*Прыжок сообщает о конце прокрутки раньше, чем список переложен.* Первая
проверка «какой блок сверху» это и показала: по горячим следам сверху виден
ещё старый блок. Считаем следующим кадром.

*Повторный показ того же вида состояния заново не создаёт* — это сбило первую
проверку показа текста: `pumpWidget` второй раз не вызывает `initState`, и
место чтения не ставилось. В приложении такого нет: `F5` меняет виджет целиком.
В проверке показ теперь снимается насовсем между заходами.

*Плавность убралась вместе с прикидкой, а не настройкой.* Первым ответом на
«вижу анимацию прокрутки» было выключить плавность у доводки. Проверка на это
**ничего не проверяла**: на ровном документе прикидка попадает точно, доводке
нечего делать, и с плавностью и без неё выходило одно и то же. Стоило собрать
документ с высокими врезками — и оказалось, что дело не в плавности: доводка
промахивалась мимо конца списка. Починено устройством показа, а не длительностью
перехода.

*И то же самое на стороне исходника — вторым заходом.* Свёрстанный вид встал на
место, а `F5` в исходник всё ещё дёргался. Это была не плавность и не прикидка,
а ровно один кадр: поле успевало нарисоваться с начала, и только следующим
кадром прыгало на нужную строку. Шестнадцати миллисекунд хватает, чтобы глаз
принял это за прокрутку.

**Правки вида по живому чтению.** Черта `---` получила отбивку сверху, ячейки
таблицы — поля и скруглённые углы врезки, а колонки — ширину по содержимому
(§6). Последнее из списка «а есть ли общепринятый способ» и оказалось самым
дешёвым: `RenderTable` уже умеет распределять ширины по наименьшей и
наибольшей, и всё, чего не хватало, — сообщить ему эти две ширины. Мешала
только проверка по типу в самой библиотеке показа, из-за которой таблица
уезжала в горизонтальную прокрутку вместо переноса.

*Проверка на отбивку черты поначалу ничего не проверяла.* Вокруг черты и так
много воздуха, и «больше, чем между абзацами» выходило само собой. Теперь она
сравнивает один и тот же документ с отбивкой и без.

*Флажки списка задач были чёрными* — и заметил это человек, а не проверка:
своего оформления у них не было вовсе, показ рисовал значок Material цветом по
умолчанию. Теперь это тот же флажок, что в окнах.

*И тут же второй заход: флажок оказался растянут вдвое.* Показ ставит значок
пункта в коробку жёсткой ширины (`builder.dart:435`), и квадратик растягивался
поперёк неё — 24 на 16 вместо 16 на 16. Я смотрел на свой же снимок и сказал
«похоже на квадрат», не измерив; увидел это человек. Проверка теперь меряет
размер, а не разглядывает картинку.

*И третий заход — флажок стоял левее всех прочих маркеров.* Тоже увидел
человек. Оба обычных маркера у левого края не стоят: `•` показ центрует в
колонке, номер прижимает вправо, — а флажок я поставил влево. Проверка теперь
сравнивает середину флажка с серединой `•`, то есть спрашивает не «есть ли
отступ», а «стоит ли он там же, где все».

**`Home` и `End` не доводили до краёв — в обоих видах и по разным причинам.**
В исходнике они не делали **ничего**: библиотека вешает голые `Home` и `End` на
край строки, а не документа. В свёрстанном `End` уводил куда угодно, только не в
конец: предел прокрутки у ленивого списка — оценка, и на документе, у которого
вся высота в конце (короткие абзацы сверху, врезки внизу), она занижена вчетверо
— прыжок приходился на 3236 из 28836.

*Проверка на `End` была пустой ровно в этом месте.* Она требовала «уехали
дальше нуля» — а уехали-то дальше нуля, просто не туда. Теперь она требует,
чтобы **последний блок был виден**, и стоит на документе той самой формы: на
ровном оценка угадывается с первого раза, и промах не виден. Завышенная оценка
поправляется сама, поэтому «высокое в начале» проверкой быть не может — только
«высокое в конце».

*Колонка маркеров выравнивалась в три захода, и каждый раз замечал человек.*
Сперва флажок стоял левее всех — прижат влево, тогда как точку показ центрует.
Потом оказалось, что и сама точка висит не там: номер прижат вправо, а она по
центру, и зазор до текста у неё втрое больше. В третий раз — что зазор мал у
