# Правка атрибутов

**Состояние:** спецификация написана, работа не начата. Отметки по ходу — в §15.

Этап [Е2](../roadmap.md#е2-правка-атрибутов). Права, даты, владелец и
расширенные атрибуты правятся в самом приложении — на любом источнике, который
это умеет.

## 1. Чего сейчас нет

Приложение об атрибутах **рассказывает и молчит**. `Cmd-I` показывает строку
режима, восьмеричные права и все три даты
([`file-info.md`](file-info.md), §4), колонка «Атрибуты» рисует
`-rw-r--r--` — а поменять из этого нельзя ничего. Права правят в терминале,
даты не правят вовсе.

В коде это видно по одному-единственному умению. `NodeAttributesWriter` —
интерфейс с одним методом:

```dart
abstract interface class NodeAttributesWriter {
  Future<void> carryMode({required FsNode from, required FsNode to});
}
```

Он завёлся ради узкого случая: редактор пишет во временный файл и
переименовывает его на цель, а временный заводится с правами по умолчанию —
файл с режимом `600` после правки оказался бы `644`
([`elevated-writes.md`](elevated-writes.md), §5). «Перенести режим с одного
объекта на другой» — это всё, что приложение сегодня умеет делать с
атрибутами.

Под ним лежит `chmod(2)` через FFI (`fc_platform`, `local_mode.dart`) — потому
что в `dart:io` `chmod` нет вовсе: файл можно прочитать, записать,
переименовать и удалить, а права у него **только прочитать**. `utimes`,
`chown` и `xattr` нет и там.

Отсюда же второй долг. `ProviderCapabilities.preservesModified` объявлен и
**никем не спрашивается** — в [`providers.md`](../providers.md), §5.3 записано
почему: «вернуть дату после переноса потоком нечем — для этого понадобится
примитив „поставить дату“». Примитив появляется здесь.

## 2. Что получается

`Ctrl-A` открывает окно правки: три группы по три флажка и восьмеричное поле
рядом, владелец и группа, две даты, список расширенных атрибутов. Флажок
`Recursive` пускает правку внутрь каталогов — работой, с прогрессом, отменой и
обычными вопросами при отказах.

**Расширенные атрибуты — часть первой версии, а не приложение к ней.** На macOS
ими помечено всё подряд: карантин Gatekeeper (`com.apple.quarantine`), из-за
которого скачанный файл встречают вопросом; цветные метки Finder; `com.apple.
metadata:*`. Файловый менеджер, который их не показывает, рассказывает о файле
неправду — причём ровно в том месте, где человек пришёл разбираться, почему
файл ведёт себя странно.

## 3. Два вопроса, а не один: прочитать и назначить

### 3.1. Значение границы: `NodeAttributes`

Экранная сторона провайдеров не видит вовсе — там только значения
([`client-server.md`](client-server.md), §4). Поэтому у окна должно быть
значение, в котором лежит **и что сейчас, и что вообще можно менять**.

```dart
/// Всё, что можно править у объекта, — прочитанное **сейчас**.
class NodeAttributes {
  /// Режим целиком; 0 — режима у источника нет вовсе.
  final int mode;
  final String modeString;

  /// Числами — так их знает всякий источник.
  final int? uid;
  final int? gid;

  /// Именами; пусто — источник имён не знает, и показывается число.
  final String owner;
  final String group;

  final DateTime? modified;
  final DateTime? accessed;

  final List<Xattr> xattrs;

  /// Что из этого источник даст поменять.
  final bool canEditMode;
  final bool canEditTimes;
  final bool canEditOwner;
  final bool canEditXattrs;
}

/// Один расширенный атрибут: имя и байты. Не строка — значением бывает что
/// угодно, и `com.apple.FinderInfo` это ровно 32 двоичных байта.
class Xattr {
  final String name;
  final List<int> value;
}
```

**Читается заново, а не берётся из строки списка.** В `FileEntry.attributes`
лежит режим с последнего чтения каталога, и править по нему — значит вернуть
файлу права, которых у него уже нет. Это та же причина, по которой `carryMode`
читает режим у самого объекта, и записана она там прямым текстом.

**Умения — значениями, а не вопросом к источнику.** Окно должно погасить поля
**до** того, как человек в них наберёт, а спрашивать «умеет ли» ему некого:
`SourceInfo` описывает панель целиком, а разговор идёт об одном объекте — и
внутри одной панели бывает по-разному (ссылка и её цель, объект чужого
пользователя).

### 3.2. Примитивы провайдера

Три **раздельных** необязательных интерфейса в `fc_core_api`. Раздельных
потому, что они бывают порознь: `sftp` умеет режим, владельца и даты, но не
знает ни расширенных атрибутов, ни имён пользователей.

```dart
/// Читать и назначать обычные атрибуты объекта.
abstract interface class NodeAttributesEditor {
  /// Атрибуты объекта прямо сейчас — та их часть, которую знает сам источник.
  ///
  /// Расширенных атрибутов здесь нет: их читает [NodeXattrEditor], и целое
  /// складывает ядро (§3.4).
  Future<NodeAttributes> readAttributes(FsNode node);

  Future<void> setMode(FsNode node, int mode);

  /// null — не трогать эту дату вовсе.
  Future<void> setTimes(FsNode node, {DateTime? modified, DateTime? accessed});

  /// Числами, а не именами: `chown(2)` и SFTP принимают только числа, а имена
  /// знает не всякий источник. Имя разрешает [UserDirectory].
  Future<void> setOwner(FsNode node, {int? uid, int? gid});
}

/// Расширенные атрибуты.
abstract interface class NodeXattrEditor {
  Future<List<Xattr>> readXattrs(FsNode node);
  Future<void> setXattr(FsNode node, String name, List<int> value);
  Future<void> removeXattr(FsNode node, String name);
}

/// Словарь пользователей машины: имя по числу и число по имени.
abstract interface class UserDirectory {
  Future<String> userName(int uid);
  Future<String> groupName(int gid);
  Future<int?> userId(String name);
  Future<int?> groupId(String name);
}
```

Про умение говорит **наличие интерфейса**, а не флаг — то же правило, что у
`NodeEditor` и `LinkEditor` ([`providers.md`](../providers.md), §5.3): про флаг
можно соврать, про отсутствие метода нельзя. Отказ по ходу дела — это `FsError`
из вызова, и он про права, а не про умение.

### 3.3. `NodeAttributesWriter` исчезает совсем

Сегодняшний `NodeAttributesWriter` — это один метод `carryMode(from, to)`, один
реализующий провайдер и одно место вызова (`editor_saving.dart`). Оставлять его
рядом с `NodeAttributesEditor` — хоть соседом, хоть предком — значит держать в
контракте два имени про одно и то же. Ровно за это приложение уже платило
отладкой (`canWrite` и `canWriteTo`), и повторять незачем.

**«Перенести режим» — не умение, а сложение двух других:** прочитать у одного,
назначить другому. Поэтому оно перестаёт быть методом контракта и становится
расширением над ним:

```dart
extension CarryMode on NodeAttributesEditor {
  /// Перенести режим доступа с [from] на [to].
  ///
  /// Читается **сейчас**, у самого объекта: атрибуты в узле — с последнего
  /// чтения каталога, и назначать по ним значило бы вернуть права, которых у
  /// файла уже нет.
  ///
  /// **Не бросает.** Это сохранность прав, а не само сохранение файла, и
  /// ронять из-за неё уже записанное хуже, чем оставить права по умолчанию.
  /// Тем этот вызов и отличается от [setMode], который об отказе обязан
  /// сказать: там о правах спросили прямо.
  Future<void> carryMode({required FsNode from, required FsNode to}) async {
    try {
      final mode = (await readAttributes(from)).mode;
      if (mode != 0) {
        await setMode(to, mode);
      }
    } on FsError {
      // Источника уже нет или назначить нечем — переносить нечего.
    }
  }
}
```

Выигрыш не только в одном имени вместо двух. Правило «молча, потому что это не
само сохранение» сегодня живёт **внутри реализации** локального провайдера — то
есть каждый следующий источник обязан догадаться о нём сам. Теперь оно записано
один раз и достаётся всем.

Место вызова в редакторе меняется на одну строку: `provider is
NodeAttributesEditor`, дальше тот же `carryMode`.

### 3.4. Целое складывает ядро, а не провайдер

`NodeAttributes` собирается из трёх источников, и ни один не знает об
остальных:

| Откуда | Что даёт |
|---|---|
| `NodeAttributesEditor.readAttributes` | режим, `uid`/`gid`, даты и три первых умения |
| `NodeXattrEditor.readXattrs` | список расширенных атрибутов и `canEditXattrs` |
| `UserDirectory` | имена владельца и группы по числам |

Складывает их `ContentHub`, отвечая на `ReadAttributes` (§4.1). Это тот же
приём, которым окно сведений собирает разделы от нескольких провайдеров: **шелл
складывает, умеющие рассказывают**.

Заодно это отвечает на вопрос, зачем `readXattrs` отдельно, если у значения уже
есть поле `xattrs`: расширенные атрибуты стоят двух-трёх системных вызовов на
объект, и читать их там, где спросили один режим, не нужно. `carryMode` —
первый же такой случай.

### 3.5. Расхождения с роадмапом — и почему

Роадмап предлагал одно имя и другую подпись:

```dart
abstract interface class NodeAttributesEditor {
  Future<void> setPermissions(FsNode node, int mode);
  Future<void> setTimes(FsNode node, {DateTime? modified, DateTime? accessed});
  Future<void> setOwner(FsNode node, {String? owner, String? group});
}
```

* **`NodeAttributesWriter` не остаётся ни соседом, ни предком** — он исчезает
  совсем, а `carryMode` становится расширением (§3.3). Роадмап писался, когда
  этого интерфейса ещё не было, и вопрос «что с ним делать» в нём просто не
  стоял.
* **`setPermissions` называется `setMode`.** Режим — это не только девять битов
  прав: там же `setuid`, `setgid` и sticky, и слово «permissions» о них молчит.
  В модели поле уже зовётся `mode`.
* **Владелец назначается числами.** `String? owner` подразумевает, что имена
  знает тот, кто назначает, — а их не знает ни SFTP (сервер отдаёт `uid`), ни
  архив. Разрешение имени в число — отдельное умение, и живёт оно в
  `UserDirectory`; там, где словаря нет, поле принимает число, и это честно.
* **Появилось `readAttributes`.** В роадмапе интерфейс только назначает —
  значит, окно заполнялось бы из строки списка, то есть из устаревшего. См.
  §3.1.

## 4. Чтение — просьбой, запись — работой

Разница не косметическая. Прочитать атрибуты одного объекта — это вопрос с
одним ответом; назначить их дереву на десять тысяч файлов — это долгая работа,
которая отчитывается, спрашивает и прерывается. Складывать их в одно значило бы
либо возить прогресс через ответ, либо ждать конца обхода молча.

### 4.1. Чтение: `ReadAttributes`

Пара запрос-ответ в протоколе, по образцу `CheckWriteAccess`/`CoreFlag`:

```dart
/// Атрибуты объекта — прочитанные сейчас, а не те, что приехали со списком.
final class ReadAttributes extends CoreRequest {
  const ReadAttributes(this.entry);
  final EntryRef entry;
}

final class CoreAttributes extends CoreReply {
  const CoreAttributes(this.attributes);
  final NodeAttributes attributes;
}
```

* Ядро отвечает в `ContentHub` — там уже есть аренда источника, разрешение
  `EntryRef` в узел и разбор `provider is X`; разбор просьбы — в `CoreServer`
  рядом с `case CheckWriteAccess`.
* Экран спрашивает через `Session.readAttributes(FileEntry)` — рядом с
  `canWriteTo` и `contentOf`. Спрашивают у **сессии**, потому что строка
  принадлежит ей: цель бывает из другого каталога, и адресуется она тем же
  `EntryRef`, что и всё остальное ([`operation-targets.md`](operation-targets.md), §4).

Источник не умеет ничего — ответ приходит с нулевым режимом и четырьмя `false`.
Отказ (`FsError`) остаётся отказом: окно показывает его текстом, а не пустыми
полями.

### 4.2. Запись: работа `attrs.apply`

Заявкой, как всё долгое ([`client-server.md`](client-server.md), §5.4). Живого
через границу не едет ничего:

| Довод | Тип | Смысл |
|---|---|---|
| `setBits` | `int` | какие биты режима поднять |
| `clearBits` | `int` | какие опустить |
| `modified` | `int?` | миллисекунды эпохи; null — не трогать |
| `accessed` | `int?` | то же |
| `uid` | `int?` | null — не трогать |
| `gid` | `int?` | null — не трогать |
| `xattrSet` | `Map<String, String>` | имя → значение |
| `xattrRemove` | `List<String>` | какие убрать |
| `recursive` | `bool` | идти ли внутрь каталогов; умолчание `false` |
| `applyTo` | `String` | `all`, `files` или `directories` |

Прогресс, отмена и `checkpoint` — как у подсчёта размеров. Отказ на одном
объекте из тысячи — вопрос словарём `TransferAnswers` (`skip`, `skipAll`,
`cancel`): он объявлен общим ровно для этого случая — «работа по многим
объектам наткнулась на один плохой», — и заводить свой было бы вторым
протоколом об одном и том же.

## 5. Правка выражается битами, а не режимом

Целей бывает несколько, и права у них разные. Послать работе готовый режим
значит выровнять по нему все объекты сразу: человек поднял `w` у группы —
а заодно молча снял `x` у того файла, где он был.

Поэтому едет **пара масок**: `setBits` — что поднять, `clearBits` — что
опустить. Бит, которого нет ни в одной, у каждого объекта остаётся своим.

```
mode' = (mode | setBits) & ~clearBits
```

Это и есть «смешанное» состояние из роадмапа, выраженное данными, а не
признаком в окне: флажок, которого не трогали, просто не попадает в маски.

Восьмеричное поле — частный случай, а не второй путь: набранное руками
значение `V` даёт `setBits = V`, `clearBits = 0o7777 & ~V`. Тем же выражается
и «одна цель»: там маски покрывают все двенадцать битов, и результат — ровно
то, что показано.

## 6. Рекурсия — довод работы, а не подробность окна

`recursive` объявлен рядом с `FileOperations.followLinks` и читается работой из
`options`. Значит правка дерева выразима **и мимо окна** — параметром команды
из палитры или из привязки, тем же приёмом, каким `file.rename` принимает
`name`.

* **Умолчание — `false`.** Правка дерева необратима, и делать её по умолчанию
  нельзя. То же правило, что у `followLinks` у переноса.
* **Сами названные объекты правятся всегда.** `Recursive` и `Apply to`
  относятся к тому, что нашлось внутри, а не к тому, что человек выбрал
  руками: он их видел и назвал.
* **`Apply to` действует только при включённой рекурсии** и отбирает, кому
  правка достанется: `all`, `files`, `directories`. Нужен он затем же, зачем в
  `chmod` есть `X`: `755`, применённый ко всему дереву, делает исполняемым
  каждый текстовый файл.
* **По ссылкам не идём.** Ссылка правится как ссылка — там, где источник это
  умеет, — а её цель может лежать вне дерева вовсе. Отдельного `followLinks`
  здесь не будет: у переноса он есть потому, что копия по ссылке — законное
  желание, а «сменить права на том конце ссылки» — это правка чужого объекта
  без спроса.

## 7. Расширенные атрибуты

**Локально — через FFI**, тем же способом и в том же месте, где уже живут
`chmod(2)` и `copyfile(3)`: `listxattr`, `getxattr`, `setxattr`, `removexattr`
из libSystem. Она загружена всегда, доустанавливать нечего.

Разница платформ здесь настоящая, и прячется она в `fc_platform`: у macOS
вызовы берут дополнительный `options`, у Linux — нет; на Windows расширенных
атрибутов не существует, и умение просто не объявляется.

**На сервере их не будет.** В SFTP версии 3 расширенных атрибутов нет вовсе:
поле `extended` в `SftpFileAttrs` — это расширения самого протокола, а не
`xattr` файла, и ни один обычный сервер их так не отдаёт. Значит
`SftpTreeProvider` не объявляет `NodeXattrEditor`, `canEditXattrs` приезжает
`false`, и раздела в окне просто нет.

Соблазн был: у приложения есть оболочка на той стороне (Ж8), и `xattr -l`
можно позвать через неё. Отказались — это вторая реализация того же умения,
разбор чужого вывода и зависимость от того, какая утилита стоит на сервере
(`xattr` на macOS, `getfattr` на Linux, ничего на BSD). Появится настоящая
нужда — заведётся отдельным умением с честным именем.

**Значение показывается текстом, если это текст.** Байты, которые целиком
разбираются как печатный UTF-8, показываются строкой и правятся строкой;
остальное — «(24 bytes)», и правка запрещена. Подсунуть человеку испорченную
строку вместо двоичных данных хуже, чем не дать её править: `com.apple.
FinderInfo` он бы этим стёр, не заметив.

**Удалить можно любой** — в том числе двоичный. Именно за этим в атрибуты чаще
всего и лезут: снять `com.apple.quarantine`.

## 8. Окно

```
┌─ Attributes ───────────────────────────────────────────────┐
│                       Owner      Group      Others         │
│  Permissions          [x] r      [x] r      [x] r          │
│                       [x] w      [ ] w      [ ] w          │
│                       [ ] x      [ ] x      [ ] x          │
│  Special              [ ] setuid [ ] setgid [ ] sticky     │
│  Octal                [ 0644 ]                             │
│  Owner                [ koldoon ]     Group [ staff ]      │
│  Modified             [ 2026-09-09 14:20:31 ]              │
│  Accessed             [ 2026-09-09 14:20:31 ]              │
│                                                            │
│  Extended                                                  │
│    com.apple.quarantine    0083;68b8…          [Remove]    │
│    com.apple.metadata:_kM  (24 bytes)          [Remove]    │
│                                                [Add…]      │
│                                                            │
│  [x] Recursive        Apply to [ files and directories ▾ ] │
│                                                            │
│                                      [ Cancel ]  [ Apply ] │
└────────────────────────────────────────────────────────────┘
```

* **Сетка прав — `CommandDialogField.stacked`.** Он заведён ровно под такой
  случай: «группа, которой столбец значений тесен» — там об этом сказано про
  девять флажков колонок, и здесь их столько же.
* **Флажок и восьмеричное поле связаны в обе стороны.** Это два вида одного
  значения, а не два поля: правка любого из них немедленно видна в другом.
* **Поле владельца принимает имя или число.** Число уходит как есть; имя
  разрешается через `UserDirectory`. Словаря у источника нет — поле показывает
  число и говорит, что имён здесь не знает, а не молчит.
* **Даты правятся текстом** в том же виде, в каком их показывают сведения:
  `ГГГГ-ММ-ДД ЧЧ:ММ:СС`. Своего календаря окно не заводит: дату файла ставят
  редко и обычно копируют откуда-то, а не выбирают мышью.
* **Раздел `Extended` виден только при `canEditXattrs`.** Не пустым списком:
  пустой заголовок — обещание, которого не сдержали (то же правило, что у
  разделов сведений).
* **Флажок `Recursive` показан всегда, но погашен**, если среди целей нет ни
  одного каталога. Не спрятан: пропадающее поле переставляет всё, что под ним,
  прямо под курсором человека.
* **Погашено и всё, чего источник не умеет.** Не спрятано — по той же причине,
  и заодно потому, что «здесь этого нельзя» — тоже сведение.
* Окно — на `FcAsyncRun` и `FcAsyncRunDialog`: форма, прогресс, вопросы и
  разбор ошибки достаются готовыми, как у переноса и удаления.

**`FcCheckbox` учится третьему состоянию.** `bool? value`, где null —
«смешанное»; `Space` водит по кругу `смешанное → включено → выключено`. Правка
общая, а не для этого окна: то же понадобится меню видимости колонок.

## 9. Клавиши

| Клавиша | Команда | Когда |
|---|---|---|
| `Ctrl-A` | `file.attributes` | есть цель, и источник умеет хоть что-то из четырёх |

`Ctrl-A` — привычка Far Manager, где за ней ровно эти самые атрибуты файла.
Обоих «маковских» кандидатов уже занял этап Е1: `Cmd-I` и `Alt-Enter` открывают
сведения, и отбирать их у чтения ради правки нельзя — смотрят чаще, чем правят.
`Cmd-A` тоже занят, и не спорит: это «пометить всё».

В окне сведений появляется кнопка `Edit…` — рядом с `Calculate`. Она есть
только тогда, когда есть команда `file.attributes`: модуль выключен — кнопки
нет вовсе. Это то же правило, по которому в настройках нет кнопки редактора
тем без модуля редактора тем (роадмап, В3).

## 10. Где живёт

| Пакет | Что в нём появляется |
|---|---|
| `fc_api` | `NodeAttributes`, `Xattr`; `ReadAttributes`/`CoreAttributes` в протоколе |
| `fc_core_api` | `NodeAttributesEditor`, `NodeXattrEditor`, `UserDirectory`; расширение `carryMode`; `NodeAttributesWriter` убран |
| `fc_ui_api` | `Session.readAttributes` |

| `fc_local_fs` | объявляет все три умения и делегирует платформе; свой `carryMode` убран |
| `fc_editor` | одна строка: `provider is NodeAttributesEditor` вместо прежнего имени |

| `fc_ui_kit` | третье состояние у `FcCheckbox` |

Модуль обеих половин, `id: 'fc.attributes'`. Выключили — пропали команда,
клавиша, работа и кнопка в сведениях; примитивы провайдеров остаются и никому
не мешают.

**Разбор `/etc/passwd` — аванс к [Б4](../roadmap.md#б4-права-владелец-и-группа).**
Тот же словарь понадобится колонкам владельца и группы, и заводить его дважды
незачем. Кэш на время работы приложения: звать `id` на каждую запись каталога —
это процесс на файл, и об этом в Б4 сказано отдельно.

## 11. Что умеет какой источник

| Источник | Режим | Даты | Владелец | xattr |
|---|---|---|---|---|
| локальная ФС | да | да | попытка (обычно откажут) | да |
| ssh | да | да | попытка | нет: в протоколе их нет |
| zip, tar, 7z | нет | нет | нет | нет |
| находки, дерево | по источнику самой строки | | | |

Архивы не объявляют ничего: правка записи в архиве — это пересборка целиком, и
разговор о ней принадлежит Ж6, а не этому этапу. Команда там выключена, и
панель показывает это так же, как показывает недоступные файловые операции.

## 12. Решения

* **Владельца обычно сменить нельзя — и мы не притворяемся.** На `chown` нужны
  права суперпользователя, отказ приходит от системы и показывается как есть.
  **`sudo` здесь не зовём:** `Elevation` умеет ровно одно — положить готовый
  файл на место цели, — и расширять её до «выполни что угодно от
  администратора» решено «когда появится вторая живая нужда»
  ([`elevated-writes.md`](elevated-writes.md), §8). Одна правка атрибутов в
  системном каталоге такой нуждой не стала: чаще всего меняют свои файлы.
* **Долг `preservesModified` закрывается сам собой.** Примитив «поставить дату»
  теперь есть, и движок переноса может восстанавливать дату там, где источник
  её знает. В этом этапе он этого ещё не делает — правка движка идёт отдельно,
  со своими проверками, — но нечего мешать перестало.
* **Каталог правится тем же вызовом, что и файл.** Ни у режима, ни у дат, ни у
  владельца разницы нет, и заводить отдельный путь ради каталога незачем.
  Разница только в рекурсии, а она — довод работы.
* **`Apply` не трогает того, чего не трогали.** Открыть окно и нажать `Apply`,
  ничего не поменяв, — это работа, которая ничего не делает: маски пустые, даты
  null, списки xattr пустые. Проверяется тестом: это единственный способ
  убедиться, что «смешанное» действительно означает «не трогать».
* **Ошибка одного объекта не роняет всю работу.** Права на дереве почти всегда
  разъезжаются в одном-двух местах, и «отменить всё из-за одного» означало бы,
  что рекурсией пользоваться нельзя.

## 13. Чего в первой версии нет

* **Раздела `xattr` в окне сведений.** `NodeInfoProvider` живёт на экранной
  стороне и получает только `FileEntry` и байты (`Content`) — дороги к ядру у
  него нет вовсе. Дать её — значит менять `describe` у всех провайдеров сразу,
  а это разговор про сведения, а не про правку. Обещание
  [`file-info.md`](file-info.md), §4а остаётся в силе; пока расширенные
  атрибуты смотрят в окне правки, одной клавишей рядом.
* **ACL и флагов BSD** (`uchg`, `hidden`, `nodump`). Свои вызовы, свой показ и
  своя семантика; `xattr` закрывает подавляющую часть того, ради чего в
  атрибуты на macOS вообще заглядывают.
* **Правки прямо в окне сведений.** Сведения показывают, окно правит; две роли
  в одной раме — это то, из-за чего просмотрщик и редактор в приложении
  разъехались (`file-info.md`, §2).
* **Колонок владельца и группы** — это [Б4](../roadmap.md#б4-права-владелец-и-группа).
  Здесь заводится только словарь, которым Б4 воспользуется.
* **Отмены правки** (`Cmd-Z`). Это [Ж4](../roadmap.md#ж4-история-операций-и-отмена),
  и прежние атрибуты для неё придётся запоминать по всему дереву — отдельный
  разговор с отдельной ценой.

## 14. Проверка

**Unit.**

* Свёртка правки в маски: тронутый флажок попал в `setBits` или `clearBits`,
  нетронутый — ни в одну; `(mode | setBits) & ~clearBits` на трёх разных
  исходных режимах даёт ожидаемое.
* Восьмеричное поле и сетка флажков дают одни и те же маски.
* `mode` ↔ `modeString` ↔ восьмеричное: `0644`, `0755`, `setuid`, `setgid`,
  sticky, каталог, нулевой режим.
* Разбор `/etc/passwd` и `/etc/group`: комментарии, пустые строки, `:` в поле
  описания, отсутствующий идентификатор.
* Отбор `applyTo`: обход выдал каталоги и файлы — правка досталась тем, кому
  положено, а названный объект правится при любом отборе.
* `carryMode` после переезда в расширение делает то же: режим `600` переносится
  на временный файл; исчезнувший источник и невозможный `setMode` не бросают, а
  молчат. Сохранение файла редактором (`Г7`) проверяется прежними тестами —
  меняться его поведению здесь нечем.

**На настоящем диске** (`dependency/platform/test`, по образцу
`local_file_copy_test.dart`):

* `chmod` меняет режим, `utimes` меняет дату изменения и дату доступа порознь;
* `setxattr` кладёт, `listxattr` находит, `getxattr` возвращает **байт в байт**
  (включая двоичное значение с нулями), `removexattr` убирает;
* `getxattr` у файла без атрибутов отвечает пустым списком, а не ошибкой.

**Через `testApp`.**

* `Ctrl-A` открывает окно; поля заполнены свежими значениями, а не тем, что
  приехало со списком (проверяется подставкой, которая отдаёт со `stat` не то,
  что в листинге).
* Правка флажка меняет восьмеричное поле и наоборот.
* Две цели с разными правами: расходящийся флажок в смешанном состоянии;
  `Apply` без правок не меняет ничего.
* `Recursive` выключен — правится только названное, содержимое каталога цело.
* `Recursive` включён — идёт работа с прогрессом, `Esc` её прерывает,
  сделанное остаётся сделанным.
* `Apply to = только файлы`: права файлов внутри изменились, права вложенных
  каталогов — нет, права самого названного каталога — да.
* Среди целей одни файлы — флажок `Recursive` погашен.
* Команда с параметром `recursive: true` мимо окна делает то же самое.
* Отказ на одном объекте из десяти — вопрос `Skip / Skip all / Cancel`,
  остальные доходят; `Skip all` больше не спрашивает.
* Смена владельца без прав — ошибка показана как есть, окно не закрылось.
* Источник без умения (zip): команда выключена. Источник без расширенных
  атрибутов (ssh): раздела `Extended` нет, остальное правится.
* Окно сведений показывает кнопку `Edit…`; без модуля `fc_attributes` её нет.
* Приложение собирается **без** `fc_attributes`: `Ctrl-A` ничего не делает,
  панели и сведения работают.

**Живой ssh** — на том же хосте, что и остальные (`FC_SSH_TEST_HOST`),
пропускается без него: режим и даты меняются, чтение возвращает изменённое.

**Живьём, руками:** `com.apple.quarantine` на скачанном файле виден, снимается,
и после этого файл открывается системой без вопроса.
